# Harness Orchestrator

This branch holds the stable-beta rebuild of the harness plugin. The 0.6.0 engine is removed here, and the new engine is not usable yet. Parts of the old engine come back only from the reuse list in the design, each with a behaviour test shown failing first. The released 0.6.0 code stays on `main`.

Install: [docs/INSTALL.md](docs/INSTALL.md) (short guide, with a multi-worker recipe).

## Tested with

Flow systems tested with the harness so far: the shipped `basic` flow and the `gsd` flow (GSD), in the test suite with a fake runtime. Other flow systems may work, through an own flow (`bin/harness flow copy basic <new>`), but they are not tested. This list is updated from the evaluation results before the release.

## Joining a project that already uses the harness

You found a `.harness/` folder in a project.

- **You do not want the harness:** ignore the folder and work as usual. Nothing in it runs by itself, adds a git hook or changes your build, tests or commits, so your work is not blocked. The harness acts only inside its own commands.
- **You want the harness:** install the plugin ([docs/INSTALL.md](docs/INSTALL.md)), open Claude Code in the project and run `/harness:config`. It offers the committed configs (`.harness/config.json`, or `.harness/config.<name>.json` named for their owner) and records your choice in `.harness/local.json`, which stays on your machine. Until you confirm a config, no run starts (H-072).

`/harness:config` can also write a short README into the project's `.harness/` folder (`templates/harness-folder-README.md`) that says the same to newcomers. The project's own README is not changed.

## Engine entry point

The engine has one entry script: `bin/harness <verb> [args]`.
Current verbs are `version`, `help`, `selftest`, `config`, `run` (new, start, tick, wait, status, stop, resume), `state`, `tickets`, `intake`, `session`, `slot`, `flow`, `loop`, `screen`, `lifecycle` and `autonomy`.
Run `bin/harness help` for the list.

## Ticket queue

`bin/harness tickets <verb>` runs the ticket queue. Run `bin/harness tickets help` for the verbs.
It has two backends: GitHub issues with one `<prefix>:<state>` label, and local files in a folder.
The five states are `ready`, `in-progress`, `blocked`, `needs-review` and `done`.
Every state change leaves exactly one state label.
Ticket titles, bodies and comments are printed only inside the untrusted fence.
On GitHub, `show` keeps a comment only when its author has write access (the harness's own comments, and recorded answers by a writer, count); any other comment becomes one line `--- comment <n> by <login>: left out (no confirmed write access) ---` (H-018, D9).
`add … ready` and `release` print a note when the Outcome, Scope or Acceptance criteria heading is missing, and go on (D8); only an empty body is refused.
`intake <run> text <id>` is the ticket text for a session: the description as picked up when the work started, and the writers' comments (D37-INTAKE-7).
A local ticket file has a `body-lines` header field; comment records are read only after the body, so body text never passes for a record (H-028, D13).
A report is always a new comment; no comment is edited or deleted.
Settings: `HO_TICKETS_SOURCE` (`local`, `github` or `adapter`, see Intake), `HO_TICKETS_ADAPTER`, `HO_TICKETS_REPO`, `HO_TICKETS_DIR`, `HO_STATE_PREFIX` (default `harness`), `HO_TICKET_LOCK_WAIT` and `HO_TICKET_LOCK_STALE`.

- **Comment format.** Every comment the harness writes has one form (H-025, D13): a visible first line `**<role>: <event>**`, a short body, and a hidden machine line `<!-- harness:v1 {...} -->` as the last line. The machine line is trusted only on a comment from the harness's own account, which is the signed-in tracker account; if that account cannot be read, no machine line is trusted. A body line that looks like a machine line gets a visible `[text] ` prefix. `comments <id>` prints what the engine reads back: the platform login, whether the comment is the harness's own, the author (an own comment's `author` field wins, H-034) and the machine fields.
- **Questions.** `ask <id> <file>` posts the questions as one numbered comment and moves the ticket to `blocked` (H-032). Inside a session it records the question in the run ledger, and the next intake tick closes that session gracefully. If that close fails, the tick prints `close-failed <session>` and writes one `owner-action` ledger line once; later ticks try the close again without a new report.
- **Steps.** `step <id> <step> <result>` records a finished step with its result, `commit:<sha>` or `file:<path>`. `resume <id> --repo <dir> <steps...>` prints the first step whose record is missing or whose result does not exist (H-028, D2).
- **Unblock.** `unblock <id>` returns a blocked ticket to `ready` only for a signed-in account with write access (H-031). A person unblocks: from inside a harness session (`HO_SESSION_ID` or `HO_SESSION_NAME` set) it is refused with exit 77, as `autonomy approve` is. On GitHub a person unblocks by setting the ready label; the intake tick checks who set it.
- **Structure.** `template` prints the four headings the plugin writes: Outcome, Scope, Acceptance criteria, Checks (D6). `/harness:add` grills first, then creates the ticket through `tickets add` (H-005, H-006, H-015).

## Intake

`bin/harness intake <run-dir> tick|poll|interval` takes labelled tickets into work. A script polls, not a model (D4). With local tickets and `HO_TICKETS_DIR` unset, it reads `<run's project>/.harness/tickets`, wherever it is called from.

- **Trigger.** Only the ready label puts a ticket into work (H-002). The trigger author is the actor of the newest `labeled` event for that label. The ticket's current labels must still hold the ready label just before the claim; a label removed during the tick withdraws the ticket (one `pickup-skipped` ledger line, no output line).
- **Order at pickup (D2).** First the write-access check: `write`, `maintain` or `admin` passes; triage, read, an unknown person or a failed query counts as read-only, and the ticket moves to `needs-review` with one status comment (H-008, H-009, H-011). A configured target repository (`tickets.target_repos`) that the ticket text (title or body) names needs the same access (D37-INTAKE-9); a ticket that names none needs it on every configured target. If the text cannot be read, the ticket is not claimed: one `error <id>` line and a `pickup-error` ledger line report it, and it stays ready for the next poll. A bot is judged by its own access, with no allow-list, until OPEN-INTAKE-1 is answered. Then the claim and its comment. Then the readiness check.
- **Readiness.** At every pickup the main runtime judges the fenced ticket text, with no tools and without a terminal, against `tickets.required_content` (default: outcome, done-check, scope; H-012, H-013, D6). The verdict goes to the run ledger. Ready prints `start <id>` for the orchestrator. Not ready posts the judge's questions as numbered items and blocks the ticket. A verdict that cannot be read moves the ticket to `needs-review`. The judge's command line comes from the runtime profile, never from a config. The ticket text is untrusted and the judge's questions are posted to the ticket, so the judge gets nothing to read secrets with. It runs with the profile's `sandbox.no-tools` flags (for Claude Code: no built-in tool, no MCP server, no skill or command, no user or project settings and no CLAUDE.md, plan mode), from a new empty folder outside the project that is removed afterwards. At most 10 questions of at most 300 characters each reach the ticket, and a question that holds the person's home folder path is dropped. A runtime profile without `sandbox.no-tools` (the shipped `codex` profile has none) gives no verdict, and the ticket moves to `needs-review`.
- **Not ready (H-016, D7, D37-INTAKE-5).** `tickets.readiness.on_not_ready` is `ask` or `assume`; when it is not set, the run's autonomy profile decides: `full` assumes, every other profile asks. `ask` turns every gap into a numbered question, blocks the ticket, and the tick takes the next one. `assume` fills the gaps the judge can infer and lists each assumption in one `assumptions` comment before the work starts; a question only a person can answer still blocks the ticket. The mode is in each `readiness` ledger line. Any other value exits 78.
- **Working brief (H-014, D8, D37-INTAKE-4).** A ticket that starts gets the judge's structured version (Outcome, Scope, Acceptance criteria, Checks, with inferred checks): by default as a new `Working brief` comment, with the description left as picked up. `tickets.normalize: "body"` replaces the description instead; `"off"` writes none. A judge that wrote no brief leaves a `brief-missing` ledger line and never blocks the pickup. The brief is cut to 6000 characters, control characters are removed, and a brief that holds the home folder path is dropped.
- **Changes through comments (H-019 to H-023, D9).** Each tick reads new comments on the in-progress tickets this run picked up (GitHub). The harness's own reports (its account, ending in a machine line) are never a change; a plain comment from the same account is a person's. A comment from a person without confirmed write access becomes a new ticket in `needs-review` that names the source ticket and comment (H-021, D37-INTAKE-2); the running work does not change. A writer's comment follows its first line `harness:apply` or `harness:new-ticket`, else `tickets.changes.mode` (`apply` default, `new-ticket`, `ignore`; anything else exits 78). `apply` after the ticket's lane merged (a `merge-confirmed` line) becomes a new linked ticket instead (D37-INTAKE-6). An applied change that names a configured target repository where its author has no confirmed write access moves the ticket to `needs-review` with one comment naming it (D37-FLOW-8). Otherwise the change is saved, fenced, as `<run>/notes/<ticket>/<n>.md`, and the next `state <run> begin --ticket T --step S` prints `change <note-file>` once for it (H-023, D37-INTAKE-3); the orchestrator hands it to the worker and returns the ticket to its execution step. Tick lines: `change-applied <id>`, `change-ignored <id>`, `change-ticket <id> <new-id>`. A description edit is no change (D37-INTAKE-7): the first one gets one comment asking for a comment; later edits get none.
- **Trackers without labels (H-007, H-010, D1, D37-INTAKE-8).** `HO_TICKETS_SOURCE=adapter` with `HO_TICKETS_ADAPTER=<program>` (from the caller's environment, never a project config) reads an external tracker through a small adapter program: `list`, `view <id>`, `set-status <id> <status>`, `set-body <id> <file>`, `comment <id> <file>`, `trigger <id> status|text` (JSON on stdout; `tests/fake-bin/fake-tracker` is the reference). `tickets.status_map` maps the five states to the tracker's own statuses; `in-progress`, `blocked`, `needs-review` and `done` are required and distinct. With no status for `ready`, a line `harness:ready` in the ticket text is the last-resort trigger. The trigger's author is the e-mail the tracker reports for whoever set the status or wrote the text, matched through the identity map in the user config only: `"identities": [{"account": "<login>", "emails": ["..."]}]` (case-insensitive; no e-mail, no entry or an e-mail in two entries is unmapped). The mapped account needs write access on every `tickets.target_repos` repository; an unknown author or a read-only one moves the ticket to `needs-review`. In this beta the adapter backend serves intake (`ids`, `list`, `show`, `comment`, `ask`, `block`, `review`); steps, answers and the change watch need the GitHub backend.
- **Answers (H-033 to H-035, D14, D37-COMMENTS-1 to 3).** Each tick reads the replies after the newest numbered-question comment of a blocked ticket (GitHub). A reply from a person with confirmed write access returns the ticket to `in-progress` with one status comment and prints `resume <id>`; the orchestrator resumes the session by ID once or starts a new one (D14), and `tickets resume` checks each step's real result. A reply from anyone else (read-only, unknown, access that cannot be read) is not applied: the ticket moves to `needs-review` with one comment, and a writer's later reply revalidates and resumes it. A recorded answer (`tickets answer <id> <login> <file>`) counts as its author's; `tickets answer <id> - <file> <sender-id>` records an answer from a sender who cannot be mapped, which is never applied. An author field in a person's own comment is ignored (D13). An old answer never resumes a ticket that reached `needs-review` another way.
- **Urgent ticket (H-083, H-084, D3).** A writer's `harness:urgent` label on a ready ticket puts it first; a reader's urgent label gives no priority (`urgent-refused` ledger line). With a free worker slot it starts at once (`urgent-start`). With none, the newest lane of the run pauses: `<run>/pauses/<ticket>.json`, and `state begin` refuses that ticket's next step (exit 75), so it stops after its current step; `tickets.urgent.pause: "hard"` also closes its sessions at once. The urgent ticket waits (`urgent-waiting <id>`) for the freed slot, so the worker cap is never exceeded (H-105). One urgent ticket at a time: another waits until the first is no longer in progress or blocked. A pause is let go (`unpause <id>`) once its urgent ticket is no longer ready, in progress or blocked.
- **Unblock.** A writer's ready label on a blocked ticket, newer than its blocked label, unblocks it. Any other ready label on a blocked ticket is removed, and the ticket stays blocked.
- **Failure after the claim.** If a tracker step fails after the claim, the ticket moves to `blocked`, so no ticket stays in progress without a worker. One `error <id>` line and one `pickup-error` ledger line report it. A writer's ready label takes it again. If the move to `blocked` fails too, one `owner-action` ledger line says what to do.
- **Ended run.** After a run ends (a `run-end` ledger line with no later `resume`), `tick` prints `ended` and claims nothing; `tick` and `poll` exit 75, as for a stop. The stop and the run end are checked again before each claim, so a stop recorded during one ticket's readiness check lets no further ticket be claimed in that tick (D25a).
- **Stray ready label.** A ready label on a ticket that is already `in-progress` or `done` is no new pickup. The ticket keeps its state, the ready label is removed, and one `pickup-skipped` ledger line records it. On a `needs-review` ticket a writer's ready label is the approval, and pickup goes on (H-011).
- **Timing.** `tickets.poll_seconds` (default 60, minimum 30; anything else exits 78). Each tracker error doubles the wait, up to 15 minutes; a good poll resets it. The time of the last poll is the modification time of `<run>/intake/poll.json`. `tickets.readiness_timeout_seconds` (300, 10 to 1800) limits the judge.

## Variable names

The new engine's own environment variables use the prefix `HO_` (Harness Orchestrator), for example `HO_HOME`.
It never reads any `HARNESS_*` variable from the 0.6.0 engine.
`bin/harness selftest` fails when a 0.6.0 variable is set or a 0.6.0 engine script is on `PATH`.

## Config and run state

- **Config lookup.** A project value beats a user value, and a user value beats the engine default. The project config is `<project>/.harness/config.json`. The user config is `$HO_USER_DIR/config.json`, by default `~/.claude/harness/config.json`. Only a missing key or `null` falls through to the next layer. Every config file must have `"schemaVersion": 2`; any other file is refused (exit 78) and the message names the file. The templates are in `templates/`.
- **Committed configs and the local selection (H-070 to H-072, D37-FLOW-4, D37-FLOW-5).** A project may commit `.harness/config.json` (name `config`) and configs named for their owner, `.harness/config.<name>.json`. Each machine selects one in `.harness/local.json`, which is never committed (a selector that git tracks is refused): `bin/harness config select <name>` writes it with the config's name (no path) and makes git ignore that one file through the clone's local exclude file; the shared `.gitignore` does not change. Worktrees read the main checkout's selection. With a selection the lookup reads the selected config, then the user config, then the shipped default (`templates/default-config.json`: the `gsd` flow with `openspec` requirements, English). `config select --default [--flow F] [--format openspec|none]` confirms the default without a project config; `config save-default` saves that confirmation in the user config (`confirmed_default`) for projects that commit no config. `config format none` records a declined OpenSpec setup for this project on this machine, and it wins there. `config list`, `config status` and `config language` (the agent language, `agent.language`, English by default, H-077) show the state.
- **The start check (H-072).** `bin/harness run new` calls `bin/harness config gate` first. With no selection it stops (exit 73) and asks once: it names the committed configs it found and `/harness:config`, or, with nothing configured, offers the default. A saved user default starts a project with no committed config without a question and is recorded as the source; it never accepts a committed config. A selection that names a missing or unreadable config stops too, with no fallback. With `--unattended` the stop also prints an attention line; it never picks. A config committed after a start on the default is announced once and used only after it is selected. Without a selection, `config get` and status still read `.harness/config.json`.
- **The record of the approved profile (D37-FLOW-8 (b)).** `config select <name>` also records what the person approved: the autonomy profile the committed config selects and the value it gives for each field in `autonomy/ranking/raises.json` (the profile fields, `session.permissions`, `tickets.readiness.on_not_ready`, review bots, external review and its wait limits, and the "always a human" paths), with a sha256 digest. At every run start the gate compares the committed config with the record. A raise (a dropped field counts as one), or a change the ranking cannot place, stops the run (exit 73), names the fields and asks to select the config again with `/harness:config`. A lowering is accepted and the record updated. A selection with no record (as after an upgrade) or a record that does not match its digest stops the same way. A selection is never written from inside a harness session (exit 77).
- **Run stamp.** `bin/harness run new` creates `<project>/.harness/runs/<run-id>/` with a `run.json` stamp. Every `bin/harness state <run-dir> ...` verb checks the stamp first. A folder without a valid stamp, such as a 0.6.0 run, is refused (exit 66) and nothing in it changes.
- **Run ledger.** `ledger.jsonl` in the run folder holds decisions, owner actions, stops, resumes and marker events, one JSON line each. Lines are only appended, under a lock, and every line carries the run ID.
- **Markers.** Each marker file holds the run ID. A marker without this run's ID is ignored and logged once as foreign.
- **STOP file.** `<project>/.harness/STOP` still works. It is recorded in the ledger as the default soft stop, `soft:step` (D25b), also when it appears while a looser stop is in force. A new run and `state ... resume` are refused while it exists. See Stops.

## Sessions

`bin/harness session <run-dir> <verb>` launches, lists and closes sessions of one run.

- **Launch.** `launch --role R --name N --cwd DIR --prompt FILE` (or `--resume SESSION-ID`), with optional `--account A`, `--model "a|b"` and `--ticket ID` (the ticket the session works on; it decides whether a `soft:ticket` stop lets the launch start, and is kept in the record as `ticket`). A run that has ended (its newest `run-end` ledger line is newer than its newest `resume` line) launches nothing (exit 75); `state <run> resume` opens it again. Roles are `orchestrator`, `watcher`, `worker`, `validator` and `question`. The working folder must be inside the project or a worktree of it. The engine writes a launcher to `<run>/launchers/<name>.sh` and opens it in a terminal. The launcher has a clean PATH, a guarded `cd`, the role's account and a fixed session ID. The launcher also fixes the account folder itself, so a session never takes it from the terminal (issue #119): an iTerm2 tab starts a fresh login shell, and the `ho-harness` tmux server keeps the environment of its first start. The variables come from the runtime data (`account_env`: `CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for Codex; a profile without the list uses `config_dir.env` and `transcript.root_env`). With no account configured for the role, each one is set to the caller's value, or removed when the caller has none (an empty value counts as none), so the runtime's own default folder applies. With an account, they are removed and the account command sets what it sets. A value must be one absolute path with no line break or tab, or the launch is refused (exit 65); it is a folder, never a secret, and it is written into the launcher. The record keeps the caller's values as `account_env` (`null` with an account), and `transcript_root` is worked out from the same environment. It tries each model of the chain in turn when a start fails. Each attempt writes its own process ID, so the registry holds the exact process.
- **Credentials, HOME and resume (issue #119 follow-ups).** Variables that hold a login credential (`credential_env` in the runtime data: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` for Claude Code; `OPENAI_API_KEY` and `CODEX_API_KEY` for Codex) are always removed by the launcher, so a stale key in a terminal never chooses the account and no secret is ever written to a launcher file. A person who logs in by key names it in an account: the account's `env_command` prints `ANTHROPIC_API_KEY=...`, and its output is read at launch, never stored. The command must fetch the key (for example from the keychain or a private file) and never hold it as text: the launcher file holds the command itself. The launcher exports the caller's `HOME`, so the session and the start check agree on it; an account command that sets `HOME` still wins. The account command runs without the account and credential variables of every runtime, in the launch check, the start check and the launcher alike, so a flow that mixes runtimes sees the same values everywhere. A `--resume` launch reads the record's `account` and `account_env`: every earlier record of the run with that session ID must name the same account, and with no account the same account variables, or the launch is refused (65), because the runtime finds a transcript only in the folder the session ran on. The record only checks; the values still come from the caller or the account command.
- **Registry.** `<run>/sessions/<name>.json` is the one record per session. It holds the run ID, the process ID, the session ID, the role, the account and the terminal handle. A session's identity is its process ID plus its session ID. The terminal handle is used only to reach the session. Handles can be reused: a tmux pane ID after the `ho-harness` server restarts, an iTerm2 window ID after iTerm2 restarts. So the engine tags each pane or tab it opens with a tag made new for each launch and kept in the record as `term_tag`, and with the session ID (tmux pane options `@ho_tag` and `@ho_session_id`, which need tmux 3.0 or later; iTerm2 session variables `user.ho_run`, `user.ho_session` (the tag) and `user.ho_session_id`, which need iTerm2 3.3 or later). It types into, reads or closes a pane or tab only while it carries the run, the tag and the session ID of the record, and it adds a tab to a stored iTerm2 window only while that window holds a session of this run. Before close types anything, the PID file must name the record's run, session ID and process ID, and that process's command line must hold the session ID; otherwise close leaves the session open (exit 70). iTerm2 open finds the new session by value: it reads the window IDs, or the session IDs of the window, before and after the create, inside one `tell`. If not exactly one new ID appears, open tags and closes nothing and fails (exit 70). It tags the new session only while it carries no tag yet. The tag is not the session ID, because `launch --resume <session-id>` starts a new launch with the same session ID. A resume is refused (exit 65) while a record of this run with that session ID is not closed. A record without `term_tag` is left open by close (exit 70). Every iTerm2 call reaches its window by `first window whose id is <id>` and its session by `first session of (tab <k> of <that window>) whose unique ID is <id>`, and checks the tag inside the same `tell`, right before it types, reads or closes.
- **Close.** `close <name>` refuses a record of another run (exit 66). A session whose process is proven gone is only marked closed. When this caller cannot read the process table, or can neither see the session's process nor prove it gone, close changes nothing and exits 71. A `launching` record can be closed once the launch command that wrote it has ended. A live session gets the runtime's exit command typed into its own terminal, and the close counts only when that exact process has ended. A session still busy after `session.close_timeout_seconds` (default 90) is left open (exit 1) and never forced. When the process has ended but its pane or tab no longer carries this launch's tag, the terminal is left alone and the ledger records `session-close-terminal-skipped` with the reason. `list` shows the process that runs now, also after a model fallback. Known limit: close does not clear text already sitting on the session's input line (field note B1); such a close times out and the session stays open. No process is ever matched by name.
- **Deliver.** `deliver <name> (--text T | --file F) [--id ID] [--force-send]` sends one instruction to a running session (H-101, H-099, H-137; design S8-24, D42f, D42g). Every instruction carries a short unique id, made by the engine unless `--id` is given, and the text the session gets starts with `<id>: `. An id is 6-40 characters of `a-z 0-9 -`, checked as one whole value, and is used once per run. The message route goes first: the runtime data's `message.argv`, when it names a command. A message whose outcome is unknown is never typed; a proven failure falls back to typing (H-101). After the command has started, the transcript is read with the same bounded wait in every case. If it shows the id (delivered, queued or dequeued), the result is reported and nothing is typed. A proven failure is one of two cases. Either the command could not start at all: it is missing, not executable, inside the project, or its `#!` line names a missing interpreter. Or it exited non-zero, its process group is gone, and the readable transcript has no record of the id. Only then does the typed route run, with all its checks. A timeout, an exit by a signal, an exit 0 with no proof, or an unreadable transcript is unknown: one `owner-action` line, nothing typed, no retry. A command still running at `delivery.message_timeout_seconds` gets SIGTERM on its own process group, then SIGKILL after `delivery.message_kill_grace_seconds` (default 2); after a non-zero exit, what is left of its group is stopped the same way. The typed route runs only when the engine's screen reader (`lib/screen.sh`) finds no hold on the same capture (no limit notice, trust dialog or password prompt, read with the pattern file of the session's own runtime; a hold gets 0 bytes, no Enter and no chord), and only when the screen shows the runtime's idle input line, empty, with no busy mark, and the prompt in the runtime's idle colour (`idle_prompt_sgr`). Idle is proven, never read from a missing busy mark: a narrow pane can cut the busy hint off. A prompt line without colour codes, or in another colour, reads as unknown and gets nothing typed. **iTerm2 never gets typed delivery**: its capture keeps no colours, so idle cannot be proven there, and the message route is its only route. Sessions run in tmux by default. Every line under the box must be the runtime's status area (its status line, the permission-mode line, the shortcuts hint and the agent list); any other line there reads as unknown. The status line shape in the runtime data (`status_first_line`) is taken from the owner's own status line, so another user's custom status line reads fail-closed: no typed delivery for that user until the shape is learned at setup (a follow-up). The screen is read, never probed with a key, and nothing is ever typed to wake a session. On the typed route the screen is read fail-closed. Every CSI escape code is stripped first, and a capture that still holds an escape byte reads as unknown. The input line is a prompt-prefix line right below a rule line; more than one such line reads as a draft. The box ends at the last line of the whole capture below it that equals the opening frame line byte for byte, with no line cap; a rule line of another width or character is the person's text, and with no equal line the box is not closed and reads as a draft. A session launched with a name shows it at the right end of the top rule (rule characters, a space, `ho-<role>-<name>`, a space, rule characters). That top rule counts as the plain rule of the same width only when the name is the session's own launch name from its record, so the closing line must then be that plain rule; delivery's hold check and `screen watch`, which know the session, read it the same way, so a dialog above a named box is still seen (`screen classify <file>` names no session and does not). The box is empty only if the input line holds no text (dim suggested text aside) and every other line inside the box is blank. Any other text inside it, a rule line included, is a draft, and a draft gets 0 bytes, `--force-send` included. A busy session, a dialog or any screen the runtime data does not describe gets nothing typed either, and the instruction is reported as not delivered. The text is typed without Enter and the screen is read again. The lines above the box go to the screen reader once more, so a hold that appears above a box with typed text is still seen. If those lines are all blank, the reader has nothing to judge and the screen reads as unknown, so nothing is typed; this fails safe on purpose. On a hold, or a busy mark on a delivery that is not a forced stop, no Enter is sent, and one `owner-action` line says that the text sits typed on the input line; that line holds a fixed phrase and the class word only, never screen text. Otherwise Enter goes only when the line holds exactly the typed text. Dim text after the prompt is suggested text and counts as empty on tmux; iTerm2 keeps no colours, so there it counts as a draft, and an empty iTerm2 screen reads as unknown. Text of at most `terminal.typed_max_bytes` bytes (default 800, at most 1000, counted in bytes) inside the safe character set is typed as it is. Any other text goes into `<run>/messages/<id>.txt` (mode 600, written to a temp file and linked into place), and a short line that names the file is typed instead. An instruction counts as delivered only when the session's transcript records a user turn whose own text carries the id, a queued-command record that carries it, or a reply of the session that names it. The id is matched as a literal whole word: no ASCII letter, digit, `_`, `.`, `-` or character outside ASCII may touch it, and an id glued to a copy of itself does not count. A tool result never counts, nor a user record marked `isMeta`, `isCompactSummary` or `isSidechain`, and any other transcript growth only shows the session is alive. Without a readable transcript nothing is sent. The engine does not send an id a second time by itself; a caller that sends the same instruction again uses a new id. `--force-send` is for the stop message of a hard stop only (D37-LIFECYCLE-4): the text may then be typed into a busy session, and once the transcript shows it queued, the runtime data's send-now chord (`force_send.bytes`: numbers 1-31, never 10 or 13) is sent once, while the transcript shows it queued (whatever the message command's exit status) and only when the same screen gate as typing is open (an empty input line or a busy session; never on a hold, a draft or an unknown screen), when the runtime is at least `force_send.min_version`. The version comes from the runtime path the launch checked and recorded (`runtime_path`), never from a PATH lookup. Exit 0 delivered, 1 not delivered; the ledger records each step under the id. Every program delivery runs (the message command and the runtime's version check) gets a fixed PATH: `/usr/bin:/bin:/usr/sbin:/sbin` and the program's own folder, never a project folder and never the caller's PATH. So a runtime whose interpreter lies outside the system folders and the runtime's own folder cannot be version-checked; its chord is then skipped and logged. Delivery safety settings are read from the user config only; a project config that sets one, to any value including `false`, is refused with exit 65, and a value that is not a whole JSON number in range exits 78: `delivery.wait_seconds` (30, 2 to 3600), `delivery.message_timeout_seconds` (30, 1 to 600), `delivery.message_kill_grace_seconds` (2, 0 to 30) and `terminal.typed_max_bytes` (800, 300 to 1000). `terminal.enter_delay_seconds` (2, a JSON number, whole, from 0 to 10; any other value, a string included, exits 78) is a shared terminal setting that graceful close also uses, so it may stay in the project config. Tools that read the runtime's output (the version parse and compare) run as `/usr/bin/awk`, and the version check itself runs in its own process group with a limit of 5 s; on a timeout the version is unknown and no chord is sent. The session's transcript folder (`transcript_root`) is worked out by the launcher in the session's own folder and environment and copied into the record at launch, so delivery never runs the account command; delivery reads it only from the record, never from the launcher's note. Delivery refuses a recorded folder inside the project or a worktree, or one that holds the project or a worktree, and any transcript whose own folder lies inside them, and a transcript reached through a linked folder below the recorded folder. One link is allowed: the runtime's own data folder (the fixed leading part of `transcript.glob`, `projects` for Claude Code) may be a link, as in a multi-account layout, but only while it resolves to the real folder the launcher recorded at launch (`transcript_prefix_real`, written next to `transcript_root` and copied into the record) and lies outside the project; no folder below it may be a link, and a record without that field refuses the link as before. Delivery uses a cached transcript path only after resolving it (`..` segments and folder links), and only when it lies inside the resolved folder and its file name is `<session-id>.jsonl` or a folder on its path is the session ID.
- **Your own status line (issue #108).** Typing needs every line under the input box to be the runtime's status area, and the shipped shapes know only the runtime's own status line, so a custom status line reads as unknown and nothing is typed (the refusal names the fix). `harness screen <run> learn <session>` reads that session's idle screen once, read-only, with every other check of the delivery screen gate still in place. For each line under the box that no shipped shape reads it learns a shape: the line's fixed marks in order (any non-ASCII symbol, or one of `[ ] ( ) { } < > | $`; a run of the same mark counts once), with only other ASCII text between them, so words and numbers may change but a line with other marks (a dialog, a notice) still reads as unknown. A line with fewer than two marks is not learned (exit 65); a bracket pair counts as one. A line under the box that has the anchor of one of the runtime's hold shapes is never the status area, learned or not, and is never learned (exit 75). The preview shows each line and its shape and a `CODE`; nothing is stored until `learn <session> --yes --code <code>`, which reads the screen again and stores the shapes only when they are the same. They are kept in the user folder only (`~/.claude/harness/screen/<runtime>.learned.json`, mode 600, no screen text), never in a project. They are used only while the runtime binary (its real path, size and change time) and the status line command in the runtime's own settings are the ones they were learned with; after a runtime update or a status line change they are set aside, delivery types nothing, and the person learns again. Exit 75 when the screen is not an idle screen of the runtime. Known limits: the status line command is read from the settings in the runtime folder of the caller (the one who learns and the one who delivers), so with a role account that keeps its own settings the learned shapes may not match and delivery stays off; learned lines after the first are accepted at any place under the box.
- **Proof.** `proof <name> <id>` runs the delivery check alone, for an instruction the caller sent itself, for example an orchestrator session that used the runtime's own message tool. It prints `delivered <how>`, `queued` or `none`, and exits 0 only when delivered.
- **Runtime.** The launch command, its arguments and the exit command come from the runtime profile named by `runtime.main` (see Runtime profiles). `runtime.main` must be set; the project template sets it. The same file holds the delivery data: `message.argv` (null in `claude-code.json`, because no script interface for messages between sessions is documented), where the transcript is and which records prove delivery, what the idle input line looks like, and the send-now chord.
- **Accounts.** Accounts are read from the user config only: `accounts.roles.<role>` (or `accounts.roles.default`) names an account, and `accounts.list.<name>.env_command` prints `KEY=VALUE` lines for it. A launch fails when `--account` differs from the role's account, or when the account is unknown or its command fails. A role with no account runs on the caller's account folder (see Launch), never on whatever the terminal inherited.
- **Trust boundary.** The permission mode `session.permissions` is read only from the user config or the shipped default; a project config that sets it refuses the launch (exit 65) until the local approval record of D37-FLOW-8 exists, so move it to the user config. The runtime command found on PATH must not be, or link to, a file inside the project, a configured `repos[].worktrees_dir` or a git worktree of the project; otherwise the launch is refused (exit 65) and names the path.
- **Terminal.** `terminal.app` is `auto`, `iterm2` or `tmux`. With tmux the harness uses its own server (`tmux -L ho-harness`) and one tmux session per run, named `ho-<run-id>`; attach with `tmux -L ho-harness attach -t ho-<run-id>`. Other settings: `session.permissions` (user config only, default `bypass`), `session.boot_timeout_seconds` (120), `session.boot_grace_seconds` (45), `session.fatal_hold_seconds` (30), `terminal.enter_delay_seconds` (2, a JSON number, whole, from 0 to 10), and `models.<role>` for the default chain. The delivery settings are listed under Deliver.

## Liveness

`bin/harness session <run-dir> status [name]` reports facts, one JSON line per session; the orchestrator judges them (D20).

- **Verdicts.** `working`: the recorded process is alive and its command line holds the session ID. `starting`: no session process runs, but the launch command or the launcher of this launch is alive (a launch waiting for a slot, an account command, a model fallback). `dead`: every recorded process of the session is proven gone (the launch command, the launcher and the session process); a `running` record then turns `dead` once, with one `session-dead` ledger line. `closed`. `unknown`: the record or the process table cannot be read, or a process can neither be seen nor proven gone; this is never reported as `dead`.
- **Proof of an end.** The age of a record is never evidence. The launch records its own PID and start time (`launch_pid`, `launch_start`) and the launcher writes `<name>.launcher` before anything slow, so a reused PID never counts. A process is gone only when `ps` shows that PID with another start time (or without the session ID), or when `ps` shows nothing and the kernel answers "No such process" to `kill -0`; a probe that succeeds or is refused gives `unknown`. A launcher that ends writes `<name>.ended` (or `<name>.failed` when it gives up), which proves that no session of that launch runs. So a caller whose view of the process table is narrower than the sessions' (a sandbox) reads `unknown`, never `dead`. On Linux the record names its PID namespace, and a caller in another namespace reads `unknown`.
- **Silence is not death.** A session whose transcript has not changed for hours still reads `working` while its process lives. The transcript age is a number in the report and never changes the verdict. There is no stall rule.
- **Hook log.** The plugin's `hooks/hooks.json` declares seven events (`SessionStart`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop`, `StopFailure`, `SessionEnd`), each calling `hooks/liveness-hook.sh` with a 2 s limit (H-089; design D37-SESSIONS-2, D42l). The script acts only in sessions the harness launched: the launcher sets `HO_HOOK_LOG` and `HO_HOOK_EVENTS`, and without them the script does nothing. It appends one JSON line per event to `<run>/hooks.jsonl` with the time (`t`, `ts`), the event, the session ID, and `tool` and `tool_use_id`, or `error` for `StopFailure`. It never stores tool input, tool output or failure text, prints nothing, always exits 0, makes no model or terminal call and never creates a folder. `status` adds `hooks` (`state`: `present`, `none`, `missing` or `unreadable`; `events`, `last_event`, `last_event_at`, `last_event_age_seconds`, `open_tools`, `tool_running`, `tools_tracked`, `stop_error`) and `quiet`. A tool call is open from its `PreToolUse` until the `PostToolUse` or `PostToolUseFailure` with the same ID, or any later `Stop`, `StopFailure` or `SessionEnd` of the session, in file order. `quiet` is the D20 flag: a `working` session with no hook event for 15 minutes; an open call holds it off for `liveness.tool_running_max_minutes` (default 60). A session with no hook records at all (for example on an account whose runtime config folder does not load the plugin's hooks) is never flagged quiet: its `quiet` stays `null`. For such a session D20 rests on the transcript and process liveness of `status` alone. It is `null` when the session is not `working` or has no readable records. Ages come from the time in each line, never from a file's mtime. Hook records never change the verdict; a dead process always wins. `liveness.hook_events` can remove events (default all seven); without `PreToolUse`, `PostToolUse` and `PostToolUseFailure` all on, open calls are not tracked. A config read that fails at launch keeps all seven on; a list that names none of the seven is reported. `liveness.tool_running_max_minutes` is capped at 10080 (one week). The `StopFailure` field holds a short error type word, else `unknown`.
- **Start check of other hooks.** `session <run-dir> hooks-check` reads the settings files the sessions will load (the runtime profile's `hooks_settings`: the user settings in the runtime's config folder, and the project's shared and local settings). It names every hook with no time limit, or one above `preflight.hook_timeout_max_seconds` (default 10), in one attention notice on stderr and records one `owner-action` ledger line, without the hook command text (H-089; design D42l). It never edits a settings file. A settings file that cannot be read as a JSON object, or whose `hooks` is not an object, is a finding too: its hooks were not checked, so the check names it, records one `owner-action` line and never prints `hooks OK`. `preflight.hooks` is `warn` (default; exit 0, the run still starts) or `stop` (exit 69 when a hook is named); any other value exits 78. Hooks declared by other installed plugins are not read.
- **Transcript and screen.** `session <run-dir> read <name> transcript|screen [--lines N]` prints the tail of the session's transcript or screen inside an untrusted fence. The transcript is found by the recorded session ID under the root the runtime file names (`transcript` in `runtimes/<runtime>.json`); the launcher works the root out in the session's own folder and environment (account variables applied, so an account may set it from `$PWD` or set `HOME`) and the launch records it as `transcript_root`; the account command runs once in the launch command (its check) and once in the launcher. The screen is read only while the pane or tab carries this launch's tag and the session ID. A line inside that names the fence (`begin` or `end`, then `session`, in any case) gets a `[session-text]` prefix, so session text cannot close the fence.
- **No typing.** Nothing in the engine types into a session to wake it (H-099). The only typed text is the exit command of a graceful close.

## Limits and slots

The engine enforces the worker cap, one heavy job at a time and the stage limits (H-104, H-105, H-107, design D26 and D26a).

- **Worker cap.** `bin/harness run new --workers N` sets it for the run. Otherwise `limits.workers` from the config is used, and the default is 1. The minimum is 1, and no maximum is shipped. The limits are fixed in `<run>/limits.json` when the run starts.
- **Worker slots.** `session launch --role worker` takes a slot under one lock before anything is opened. When the cap is reached, the launch exits 73 and writes nothing, or it waits up to `--slot-wait SECONDS`. A stop recorded while the launch waits ends the wait with exit 75, and nothing is opened. A stopped run takes no new worker slot, except for a ticket that a `soft:ticket` stop lets finish. A soft stop still gives a heavy or stage slot to a session that already runs, so its step can finish (D25a). An unknown stop state refuses every kind: `acquire` gets 75 with or without `--wait`, and the stop is read under the lock at every try. A heavy or stage `acquire --wait` also ends with 65 or 66 when its session is closed, ends or is gone during the wait; the holder is checked again under the lock at every try, so nothing is recorded for it. Close, or a session that reads `dead` or `closed`, gives the slot back; before a `dead` holder's slot is freed its close flag is written, so a launcher that has not started its session starts nothing. A failed launch gives it back only when its session reads `dead`; a session that came up anyway holds the slot until it is closed or ends. A holder that reads `unknown` keeps its slot: a record from older code, an unreadable record, a launch command that hangs. The owner's way out is `slot <run-dir> release worker --holder NAME --force`. It needs a terminal where the session name is typed, writes the close flag and a `slot-force-released` ledger line, and refuses a holder that reads `working` or `starting`, before the prompt and again after the answer. With no terminal it exits 65. The terminal check stops accidents, not a script: a program that opens a terminal passes it, so it is a speed bump, not a security boundary (D37-FLOW-8a). Use it only when you know the session's process has ended. If that process is in fact still alive, the run then has one worker more than the cap, and the close flag left behind stops that session's model fallback (a later `session close` still works). Stop a hanging launch command by its exact PID (`launch_pid` in the record) first; the slot then frees by itself.
- **Heavy work.** `bin/harness slot <run-dir> acquire heavy --holder NAME --op TYPE [--wait S]` and `release heavy --holder NAME`. The six shipped types are in `limits/heavy-ops.json`. `slot <run-dir> heavy-add TYPE REASON` adds a type for one run; it takes a name only and never changes a limit (`limits.heavy`, default 1).
- **Stages.** `acquire stage:<id>` and `release stage:<id>`; `browser` and every other stage default to 1 (`limits.stages.<id>`). A session that needs a stage slot and the heavy slot takes the stage slot first.
- `slot <run-dir> list` shows the held slots and `slot <run-dir> limits` the limits. No free-memory check is made (S8-21).

## Subscription limits (H-109 to H-112)

Design D28, D28a, D28b, D29 and S8-23. `lib/limits.sh`, `harness limits`.

- **Reading.** Each session gets the runtime's settings file argument (`status_line` in the runtime profile) with the status line command `harness limits record`. That command reads the status line JSON on stdin and keeps one reading per account in `<run>/limits/<account>.json`; outside a run it writes `<user dir>/limits/`. The launcher exports `HO_ACCOUNT`, the account label (`default` for the normal login). A harness session keeps the user's own status line: after it keeps the reading, the record command runs the status line command from the settings the session would otherwise load (`status_line.user_settings` and `.user_command`; for Claude Code, `statusLine.command` in the account's config folder `settings.json`) with the same input and prints its output unchanged. With none it prints nothing. A failure of either part never breaks the other, and the command always exits 0. Every window the account reports is kept under its own name; the 5-hour window may be missing, and that is no error.
- **Accounts.** Every label in the user config's `accounts.list` is read, plus any account with a reading in the run; with an empty list, the normal login (`default`).
- **Thresholds.** Optional, per window: `limits.thresholds.<window>`, or `limits.thresholds["*"]` for every window without its own key. A value is a percent or `{"at": <percent>, "action": <action>}`. Lookup per window: project window, project `*`, user window, user `*`. Nothing set means off, and no reserve is kept; the reserve of a window is the part above its threshold (D29). A value above 100 never triggers. Actions: `pause_spawns` (the default), `soft_stop_step`, `soft_stop_ticket`, `hard_stop`. Until hard stops are built, `hard_stop` pauses spawns and records a decision line.
- **Pause.** A worker launch in a run where a threshold paused spawns exits 74 and writes nothing. The pause stops nothing that runs. It lifts when the reading drops below the threshold, or when the window's reset time passes (the old reading then reads unknown).
- **Unknown.** No reading, an unreadable one, or a window past its reset time reads `unknown` in `limits <run> status` and is recorded once in the run ledger (`limits-unknown`). Unknown never blocks a start (H-111).
- `limits <run> check` reads every account, records changes (`limits-over`, `limits-clear`, `limits-unknown`) and runs the actions; a soft-stop action records the stop and prints its text for the caller to deliver. `limits <run> gate [role]` answers 0 or 74.
- **Endpoint read.** Off by default (`limits.endpoint_read: false`). Only the user config can switch it on and name `limits.endpoint_command`, which prints `{"windows": {...}}` for the account in `HO_ACCOUNT`. It is used only for an account with no status line reading. A project config is never read for it.

## Recovery (H-088, H-091 to H-094, H-114)

Design D14, D20, D21, D28c, D32, D37-LIFECYCLE-1, D37-LIFECYCLE-2, D37-SESSIONS-1, D42h. `lib/recover.sh`, `harness recover`.

- **`recover <run> tick`** runs the fixed order for each ticket whose newest worker session reads `dead`: leave it when a human stopped it (a STOP file or a stop in force, the ticket's state label changed away from in-progress, or the runtime's exit command typed in the transcript while no close was under way); resume the same session by its ID once, when the ID is recorded, the transcript is on this machine, the working folder exists and the runtime can resume; otherwise a new session with the context pack (`<run>/recovery/<ticket>.pack.md`: ticket text and thread inside the fence, worktree, branch, current step, step reports, old session ID). Every launch opens its own terminal tab or pane, so the new session is also the fresh-terminal step. A failed resume counts as an attempt, and the new session follows at once. A launch refused for now (73 no slot, 74 spawns paused, 75 stopped, 76 outage) is no attempt: the ticket waits for the next tick, also when recovery had already closed the old record for the resume. A run-level stop leaves the ticket only while it is in force; a ticket label changed by hand or an exit typed by a human leaves it for good.
- **Attempts.** `recovery.attempts` (3) and `recovery.waits_seconds` (`[60, 300, 900]`). When they run out, the ticket goes to `blocked` with one comment. The late attempt runs once, `recovery.late_hours` (12; `0` turns it off) after the block, while the ticket is still blocked and no stop is in force; a failed late attempt writes one ledger line and no comment. The attempt clock stops during an open wait (`wait-begin` with no `wait-end`: a limit wait or an outage) and during sleep: each tick adds at most `recovery.tick_cap_seconds` (300). The state is kept in `<run>/recovery/<ticket>.json`, so an orchestrator restart loses nothing.
- **Wait for a limit reset.** `limits <run> wait <account> [--until EPOCH]` waits until the reset time of the hit window (the open wait's recorded time, else the reading, else `limits.unknown_wait_seconds`) plus `limits.resume_margin_seconds` (60), in slices of `limits.wait_slice_seconds` (30). Exit 0: continue the run with no owner action. A STOP during the wait ends it with exit 75. One `wait-begin` and one `wait-end` line per wait.
- **Reboot.** Nothing starts by itself; the plugin installs nothing into the operating system. `recover last` names the newest unfinished run of the project. `recover <run> reopen` resumes each session whose process is gone by its recorded ID and leaves every live one; no recorded process ID is signalled. With `recovery.ask_first: true` it exits 77 and starts nothing unless `--yes` is given.

## Out-of-memory cap and usage history (H-106, H-108)

Design D26b, D37-LIMITS-1, D37-LIMITS-2, D37-LIMITS-4, D37-LIMITS-6, D37-FLOW-8. `lib/resources.sh`, `harness resources`.

- **`resources <run> oom <container-id> [--ticket T]`.** A session reports a stopped container by its exact ID. The engine runs the check command for that one container: the shipped default in `limits/oom-check.json` (the container runtime's own record), or a user-config entry `limits.oom_check.list.<label>` with `argv` (`{container}` is filled in) and a `jq` filter that must give `true`. A project config may only select `limits.oom_check.label`; one that holds a command is refused at `run new` and by the check, and nothing from it runs. A failed, slow (20 s), unclear or missing answer leaves the cap as it is. A confirmed stop lowers the run's worker cap by one in `<run>/limits.json`, once per container ID, never below 1. The configured value is not touched, and the next run starts from it. The stopped task restarts through recovery when a slot is free; when its attempts run out, the block comment names the out-of-memory cause.
- **`resources <run> sample`** appends one reading (CPU load, memory in use, process count, the run's workers) to `<project>/.harness/usage/history.jsonl`. **`resources recommend`** shows a recommended total (and 1 per stage and heavy job) only when that history holds readings with workers; it never writes a config.

## Watch script: outage monitor and orchestrator restart (H-095 to H-098)

Design D22, D23, D32, D37-SESSIONS-3, D37-SESSIONS-4. `lib/watch.sh`, `harness watch`. It runs no model session.

- **Outage monitor.** Two plain HTTP checks, the service and the internet (the runtime profile's `outage` block, or `watch.service_url` and `watch.internet_url`). The service is up when it answers below 500; the internet when it answers at all. Every `watch.up_seconds` (300) while up, every `watch.down_seconds` (60) while down. A change writes one `outage-begin` (what failed) or `outage-end` line and opens or closes a `wait` line with reason `outage`, which stops the recovery attempt clock. While an outage is open, `session deliver` sends nothing and `session launch` starts nothing; both exit 76. The last values are in `<run>/watch/state.json`.
- **Back.** After an outage the monitor looks at the orchestrator. A `StopFailure` as its last hook event sends the "service is back" message at once. Otherwise a hook event from it within `watch.back_wait_seconds` (120) is the "I am back" marker (`orchestrator-back`), and no message goes out. With no event the message goes out, at most 3 times, 120 s apart; after the third the orchestrator is closed the normal way and resumed. The monitor never writes to a worker.
- **Restart.** `watch <run> restart` is the one restart command, for the watch script and the context watcher alike. It takes a lock and leaves a live orchestrator alone. A dead one is resumed by its ID, else started fresh with `<run>/handoff.md` when it exists. At most `watch.restarts_per_hour` (3) in any hour, counted in the run ledger; with the cap used up, one `orchestrator-down` line and one owner-action line in that hour. Nothing restarts during an outage or after the run ended. A soft stop does not hold it back: `session launch` starts an orchestrator or a context watcher under a soft stop (an unknown stop state still refuses). A restart refused for now is deferred, uses no part of the cap, and the next cycle tries again.
- **Loop and supervision.** `watch <run> loop` runs the checks every `watch.cycle_seconds` (15) until the run ends, and writes `<run>/watch/watch.pid`. Every `watch.sample_seconds` (300) it adds a usage reading to the history (H-108). The orchestrator and the context watcher call `watch <run> pid-check` (0 runs, 1 not) and start the loop again when it is not running. Nothing is installed into the operating system.

## Flows

A flow config is a folder with `flow.json` and one prompt file per step. It holds the steps, their order and their runners (S8-15). Gates and permissions belong to the autonomy profile, a separate file: a `flow.json` that sets one of its keys (`gates`, `push`, `pr`, `merge` and the like) is refused, and no flow verb writes outside the flow folder (D37-FLOW-3).

Two ready-made flows ("flow profiles") ship in `flows/`: `gsd` and `basic`. Both give the default cycle (H-064): classification, discussion (grilling) only when classification finds open questions, planning, execution, code review, verification, UI check and shipping, in that order. `basic` writes every step out as a plain prompt and needs no flow system. `gsd` runs the middle steps through GSD, which must be installed; classification and shipping stay harness steps. A project's own flows live in `<project>/.harness/flows/<name>/`. A project flow may not have the name of a shipped flow, and its folder must stay inside the project.

### Requirements format (H-076, D41, D37-FLOW-7)

`requirements.format` is `openspec` or `none`; it resolves project, then user, then the confirmed default (OpenSpec, confirmed once with the flow). A recorded `none` in the local selection (`config format none`, after a declined OpenSpec setup) wins on this machine. A project without OpenSpec is a normal case, and an `openspec/` folder alone decides nothing. With `openspec`, the render adds one read-only block (`prompts/requirements-openspec.md`) to the step marked `"kind": "grilling"` (the `grill` step of both shipped flows), unless `requirements.use_in_grilling` is false. The block tells the session to read and cite the requirements and never to edit or adopt anything into them. No other step gets it, and the engine never creates `openspec/`; OpenSpec is set up only after a person's yes.

### Project setup: `/harness:ai-ready` (H-129, H-074, D33a)

`/harness:ai-ready` prepares a repository for AI development: it reviews `CLAUDE.md`, offers an `AGENTS.md` link, `SECURITY.md` and hooks where they fit, and offers OpenSpec only after a yes. It never installs or configures a flow system (D37-DISTRIBUTION-1), writes nothing under `.harness/`, and adds nothing the project would depend on: the harness installs no git hook and changes no shared file, so a clone works the same without the harness. It has no alias; the old `init` and `onboard` names point to `/harness:config`.

- `bin/harness flow list` prints the shipped and the project flows; a missing flows folder stops with exit 78. `flow check <flow>` checks the flow file, every step prompt and the role prompts. `flow steps <flow>` prints the steps that are on, one per line: number, id, `always` or `questions`, title.
- `bin/harness flow render <flow> <role> [--step <id>] [--set NAME VALUE]... [--file NAME PATH]...` prints a role prompt. The roles are `worker` (one step; needs `--step`) and `validator`. The role prompts are in `prompts/` and are the same for every flow.
- Placeholders have the form `@NAME@`. The engine fills `FLOW_NAME`, `FLOW_STEP_LIST`, `STEP_ID`, `STEP_TITLE` and `STEP_TEXT`. The caller sets `RUN_ID`, `TICKET_ID`, `TICKET_TEXT`, `BRANCH`, `BASE`, `WORKDIR`, `STEP_RESULT_FILE` and `VERDICT_FILE`. `TICKET_TEXT` must be exactly what `harness tickets fence <id>` prints for ticket `TICKET_ID`; anything else is refused (exit 65). `TICKET_TEXT` is the only value that may span lines. Any other value that holds a line break, a CR, another byte below 0x20 except tab, DEL, a Unicode line or paragraph separator (U+0085, U+2028, U+2029) or a bidi control (U+202A to U+202E, U+2066 to U+2069) is refused (exit 65). `TICKET_ID` must be a number of at most 9 digits (exit 65 otherwise). A placeholder with no value or an empty value fails the render (exit 65), and nothing is printed. Values must be UTF-8 text (anything else is refused with exit 65, never changed; `render` uses `iconv` to check this). They are inserted as they are and never scanned again, so ticket text that quotes a placeholder is safe. Each value reaches jq through a temp file, so a large ticket is no problem.
- There is no default flow. A missing or broken flow (also an empty `flow.json`) stops with exit 78 and names the flow. Engine code (`bin/`, `lib/`, `prompts/`) names no flow system, vendor, runtime or model; such names live only in data.
- Selecting the flow for a project comes later (H-069 to H-072). `HO_FLOWS_DIR` points at another folder of ready-made flows.

### Editing steps (H-066)

Edit the step list in `flow.json`. The order of the list is the order of the run.

- **Reorder** by moving a step in the list. Code review may come before shipping, where the PR opens.
- **Add** a step with its own `id`, `title`, `when` and `prompt` file, anywhere in an own flow: a version bump, a connection check, a test audit before or after code review.
- **Switch off** a step with `"enabled": false`, for example code review when a review bot reviews every PR. It leaves `flow steps`, the numbering and the step list in every prompt, and it cannot be rendered. A flow with every step off is refused.
- **Name a runner** with `"runtime": "<label>"`, a runtime profile. A step without one uses `runtime.main`.
- `"kind": "review"` marks a review-type step (code review, UI review, a second opinion). `"skills": [...]` and `"agents": [...]` name the skills and agents a step uses; the start check checks them. A step may hold only these documented keys; `flow check` refuses any other key by name. The same holds for the top level of `flow.json` and for `system`. `"install": {"<skill>": "<install step>"}` gives their install steps.

### A chosen flow system (H-067, D17, D37-FLOW-2)

A flow with `"source": "system"` points to a chosen flow system, for example GSD. Its `system` object names the system and its `link`, its `install` step, the `skills` the flow uses from it, and `steps`: the ids of the steps the system owns. The system itself is linked, never copied into the repository (H-073). Any system name is accepted (H-068).

The chosen system owns its steps. They form one block, in the order of `system.steps`. Harness extra steps go only before or after that block. Each of these stops with exit 78, names the step and names the route: a step placed inside the block, a system step out of order, a system step switched off, and a flow with `"source": "own"` that also has a `system`. The harness never merges two step lists and never moves or drops a step by itself. A system step may still name its runner.

The route is an own flow: `bin/harness flow copy <flow> <new-name>` copies any flow into `<project>/.harness/flows/<new-name>/` as an own flow (`"source": "own"`, `"copied_from": "<flow>"`). The system's skills, agents and install step stay on the steps it owned, so the start check still checks them. Copy never overwrites a project flow, refuses the name of a shipped flow and writes nothing else.

## Runtime profiles

A runtime profile is one data file per tool (D31, D37-RUNTIME-2). Two ship in `runtimes/`: `claude-code` and `codex`. A profile is read from `<user dir>/runtimes/<label>.json` first, then from the plugin's `runtimes/`. A project can never add one, because a profile holds launch lines (D37-FLOW-8). A profile lists its `modes` (`interactive`, `noninteractive`), the interactive launch (`argv`), the launch without a terminal (`noninteractive`), the `permissions` and `sandbox` flags, the `skill_call` form, `config_dir`, `session_log`, `limits`, `capabilities`, the login `check`, the `skill_paths` patterns and the `install` step.

- `bin/harness flow plan <flow>` prints each step that is on, with its runtime, mode, owner (`harness` or `system`), a note and its launch line, all from profile data: `<n> TAB <id> TAB <when> TAB <title> TAB <runtime> TAB <mode> TAB <owner> TAB <note> TAB <launch>`.
- **Mode (D30, H-102).** A step runs interactively in a terminal when its runtime can. Codex has no interactive mode in this beta, so every step on Codex runs through `codex exec`. A review step runs there with the read-only sandbox. Any other step on Codex, such as execution, runs only where the flow names Codex for it and is marked `experimental` (untested until a comparison run gives the same result).
- **Start check (H-073, H-078, D37-RUNTIME-3).** `bin/harness flow preflight <flow>` checks that every runtime the flow uses is on `PATH` (outside the project) and logged in, and that every skill and agent a step names, and for a system's steps every skill and agent of the system (`system.agents`), is installed for that step's runtime. Config folders and `{home}` follow the worker account, as in a launched session (issue #119): its variables win; with no account, the caller's environment comes next; then the profile default under the account's `HOME` (or the caller's when the account sets none). With an account, the caller's value of a runtime account variable (`account_env`) is never used, and the login check runs without it, because the launcher removes those variables before the account command. The account command itself also runs without them, in the launch check and the start check as in the launcher, so a command that falls back on such a variable (`${CLAUDE_CONFIG_DIR:-...}`) gets the same folder everywhere. Agents are found through the profile's `agent_paths`; a runtime whose profile has none cannot show an agent, so the agent counts as missing. The login check runs in its own process group with stdin from `/dev/null`, the clean PATH and a time limit of `check.timeout_seconds` (a whole number from 1 to 600, default 20). On a timeout the whole group gets TERM, then KILL after 2 s, by its exact group ID, under the worker role's account; a missing command, a non-zero exit, an output without a login and no answer in time all count as missing. The whole check runs first; then every missing item is printed in one list with its install step, and the exit is 69. Install text from a project flow is marked as not checked. Nothing is ever installed. Experimental steps are named in the output.
- Running a step without a terminal is not wired into `session launch` yet; the run loop comes later.

## Running a run: `/harness:run`, `/harness:status`, `/harness:stop`, `/harness:resume`

The four commands each call one engine verb; the control flow is in the engine (`lib/orch.sh`), not in a prompt.

- **`run start [--workers N] [--standby on|off]`** (`/harness:run`). It resumes the newest unfinished run of the project (D32). A run that a stop ended while a ticket was still in progress is not lifted: the start exits 75 and names `/harness:resume`. Otherwise it runs the start checks in order and stops at the first refusal with that check's exit code: the config gate (73, H-072), the flow preflight (D31), a new run, the hooks check (it only warns, D42l), the limits gate (74), the autonomy start check (76, 77). It then creates the run's integration branch from the checked-out branch, writes `<run>/handoff.md` (the orchestrator prompt with the engine path, D23, D24), launches the orchestrator session and starts the watch script. A refusal after the run was created ends that run (`start-refused`), so it is never resumed.
- **`run tick <run-dir>`** is one pass of the run loop; the orchestrator calls it again and again (`prompts/orchestrator.md`), with **`run wait <run-dir> [max]`** between passes. A pass starts the context watcher if it is not alive (H-098) and the watch script if it is gone, reads the limits, runs `intake tick`, and moves each taken ticket one move: the profile's gate on the step (`autonomy check step`), the limits gate, the step gate (`state begin`, which also hands over accepted ticket changes), a worker session per flow step with `--ticket`, the step result in `<run>/orch/<ticket>/<step>.result`, `tickets step`, the finalize commit and `loop ready`, the validator session, its verdict, `loop merge` when the profile allows a local merge, then `ship push`, `ship pr` and `ship merge` as the profile allows, or `autonomy end`. Each pass ends with `recover tick` and `lifecycle check`. It prints one line per action; `attention <ticket> <session> <liveness>` and `error ...` are for the orchestrator to judge. Waits (no slot, limits, a stop, a human gate) are lines, never errors.
- **Places and hand-backs.** Intake takes at most the worker cap minus the run's active tickets, because a ticket between two steps holds no session but keeps its place. A ticket that comes back after an answer or an unblock continues at its first step with no recorded result (`tickets resume`). A worker's `blocked:` question is asked on the ticket as that worker's. A validator that ends with no verdict is replaced by a fresh one, at most three in all. When the orchestrator's own tick ends the run, a detached check closes the orchestrator 5 seconds later, after its turn.
- **Engine decisions.** The engine writes the `finalize(<lane>):` commit after the last step reads `pass`, only on a clean tree, and records the last worker as the lane's worker. The validator records the test counts and its verdict itself from its session (`verify tests`, `loop verdict`). The merge facts for `ship merge` come from the engine's records; a PR with no check result is not green, so a profile that merges waits and tries again each pass.
- **`run status [run-dir]`** (`/harness:status`) reads only: the stop state, the sessions, each ticket's phase and step, the merges, the limits and the owner actions.
- **`run stop [run-dir] [--type T] [--ticket ID]... [--message TEXT] [reason]`** (`/harness:stop`) records the stop with `state stop`. A soft stop's text then goes to every worker and validator session it covers, each with an instruction id that starts with the stop id. A hard stop acts at once (see Stops). A soft stop ends the run once no session is at work.
- **`run resume [run-dir] [--yes]`** (`/harness:resume`) records a resume (refused while the STOP file exists), reopens dead sessions by their ID (`recover reopen`; `--yes` when `recovery.ask_first` is on, exit 77 without it), brings the orchestrator back (the watch script's restart path when one existed) and starts the watch script. With no run folder it takes the newest unfinished run, else the newest run a stop ended.

## Run loop and merge

`bin/harness loop <run-dir> <verb>` takes one ticket's lane to a local merge that the engine checks (H-055, H-046). It merges only into the run's local integration branch and never pushes.

- **Integration branch.** `integration --repo R --base B --worktree W` creates the branch `ho/<run-id>` at base `B` and checks it out in the new worktree `W`. Each run has one. `<run>/integration.json` keeps the last confirmed tip.
- **Completion signal.** `ready <lane> --worktree W [--ticket ID]` accepts a lane only when the tip of its branch is a `finalize(<lane>):` commit and its tree is clean. Nothing else counts as done. It records that commit, and the session ID of the session that called it (the lane's worker), and prints the verdict record path, `<run>/verdicts/<lane>/<commit>.json`. So a verdict covers one exact commit.
- **Verdict.** `verdict <lane> --sha S` records the validator's verdict, with the text on stdin. It runs only inside a launched session: it takes the session name and ID that the launcher exports, and the run's session registry must hold that session with the role `validator`. `S` must be the recorded commit. The record keeps the session ID as the verdict's author. A verdict file written any other way has no valid author and never merges.
- **Merge.** `merge <lane>` first asks the run's autonomy profile whether it may merge at all (see Autonomy profiles). Then it merges only when all of these hold. The first line of the verdict text is exactly `passed`. "passed with remarks" and "failed" never merge. The author is a session of this run whose only role is `validator` (a worker resumed under a validator record keeps its session ID and is refused), and it is not the lane's worker. The `verdicts` folder, the lane's folder and the record are no links. The lane tip is still the validated commit. Both trees are clean, untracked files included. The integration branch is checked out and is at its last confirmed tip. The run is not stopped, or a `soft:ticket` stop covers the ticket that `ready --ticket` recorded for the lane. Then the engine runs `git merge --no-ff` of that commit and confirms it from the branch ref: the new tip has the old tip and the lane commit as parents, and its tree differs from the old tip. The gate then runs on the merged tree in a throwaway worktree, in its own process group. After the gate, still under the merge lock, the engine reads the verdict again; if it changed, the merge is rolled back. A merge counts only with its `merge-confirmed` ledger line.
- **Author boundary.** The author check stops a worker that uses its own session identity, or a file in the repository, from passing as the validator. It does not stop a process of the same user, a worker included, that sets the two session variables to the validator's values or edits the run folder by hand. D37-FLOW-8a puts that outside the beta's boundary; the owner confirms this reading.
- **Failures.** Exit 65 means the merge was refused and nothing changed (or a changed verdict was rolled back). 69 means the merge would change nothing (a no-op is a failure). 70 means a conflict, a failed git check or a git error, or that the branch is left for a person. 72 means the gate failed on the merged tree. 75 means the run is stopped, the merge was stopped by a signal, or another merge holds the lock. 78 is a config error. On 65 after the gate, 69, 72, 75 and a failed merge or git check (70) the branch is put back to its old tip with `git reset --hard` inside its own worktree, never by moving the ref, and only while the branch is still checked out at its old tip or at this merge's commit, and the worktree is pristine: no uncommitted change, no untracked file and no ignored file (`git status --porcelain --untracked-files=all --ignored` is empty; the engine itself writes no file there). The reset is `git reset --keep`, which also refuses to overwrite a local change. When the branch moved, HEAD is detached or on another branch, or the worktree is not pristine, nothing is reset: it is left for a person (70), the message names the cause and never says "rolled back", and nothing is lost. For the same reason a merge is refused (65) unless the integration worktree is pristine before it starts. After a git confirmation failure only a commit that is provably this merge (parents: the old tip and the lane commit) may be undone. A tip that moved outside the engine, for example after an interrupted merge, refuses every merge until a person puts it back.
- **Signals.** TERM, INT or HUP to the caller is passed to the merge's own subshell. That subshell stops the gate's process group, rolls back as above, releases its lock and exits 75; the caller returns that code. A signal that comes while the gate's worktree is made stops the merge before the gate starts. From the `merge-confirmed` line on, a signal no longer undoes the merge: TERM, INT and HUP are ignored until the tip is written, also when they go to the whole process group (a closed terminal); the ledger line is written by a fresh shell that starts with them ignored. KILL cannot be caught or passed on: after a KILL to the caller the merge subshell runs on and may still confirm the merge.
- **Lock.** One merge at a time per run, under `<run>/merge.lock`. A lock whose holder is dead is taken over in place under `merge.lock/takeover`; a waiter never removes a lock, so it never removes another waiter's new one. A merge removes only its own lock.
- **Gate.** The engine runs the gate command itself, so the command comes only from the user config (D37-FLOW-8): `gate.list.<label>.command`. The project or user config selects the label with `gate.use`. With no gate, the merge is refused. A project config that holds a gate command is refused, and the message says where to move it.
- `status` prints the integration tip and the confirmed merges. The "passed with remarks" flow comes later (#60).

## Push, draft PR and merge confirmation

`bin/harness ship <run-dir> push|pr|merged|status` takes a ready lane to the remote (H-043 to H-046, H-050, H-051; D10, D11, S8-07). Every remote write first asks the autonomy profile; `safe` and `gated` keep everything local until a human pushes.

- **`push <lane> --ticket N --title T`** pushes the lane's finalize commit to `<prefix><N>-<short title>` on `git.remote` (default `origin`). The prefix is `git.branch_prefix`, default `harness/`. The push counts only when `git ls-remote` shows the branch at that commit.
- **`pr <lane>`** opens the PR, always as a draft (D10), at the profile's opening point `pr_open`: `after-validator` (default) needs the validator's plain `passed` verdict for the pushed commit; a step id needs that step begun for the ticket (`state begin`). The PR always links its ticket; on GitHub the body adds `Closes #N`. Only a profile that may merge marks it ready. The base is `stage.branch` when `stage.allow` is `true`, else `git.target` (default `main`).
- **`merge <lane> --facts F`** is the remote merge (H-050). It runs only when four things hold: the profile may merge, every mechanical condition holds (`autonomy check merge --facts`), and the validator's pass and the test result exist for the pushed commit. Then `gh pr merge` merges the PR, and `merged` confirms it through git.
- **Stops and re-pushes.** A stop refuses `push`, `pr` and `merge`, as it refuses `loop merge`. `merged` stops only under a hard stop. A second `push` after a fix keeps the open PR and rebuilds its Verification block. `pr` also needs a passed test result for the pushed commit (`verify tests`).
- **`merged <lane>`** confirms the merge through git: the fetched base holds the pushed commit, or the PR's merge commit is on the base and carries the same change (a squash merge, compared by patch id). An unconfirmed merge is reported as failed (exit 70) and the ticket stays as it is. After a confirmed merge the smoke test runs at once when `smoke.use` names one; its command lives only in `smoke.list.<label>.command` of the user config. The ticket is set to done only after the smoke test passes, and closed unless `close_on_merge` is `false` (then it is done and left open). A profile without post-merge steps leaves the ticket in progress for a human (exit 76). A failed smoke test (exit 72) runs `smoke.on_fail`: `fix` (default) records that a fix is due; `revert` reverts the merged change on the base and pushes it.

## Verification

`bin/harness verify <run-dir> <verb> <lane>` keeps the recorded check results of a lane and builds the Verification block from them, never from a session's free text (H-053, H-054, D37-VERIFICATION-4).

- **`record <lane> --check NAME --result passed|failed|not-done [--reason R] [--proof P]`** records one check result. A check that was not done needs a reason.
- **`tests <lane> --total N --passed P --failed F --skipped S`** (or `--unreadable`, `--no-tests`) applies the test rule (H-056, H-057, D37-VERIFICATION-3). A failed test always fails. The counts must add up. At least one test must run, unless the profile sets `allow_zero_tests`; skipped tests are not tests run. An unreadable result is never zero tests. Exit 72 on a failure.
- **`block <lane> [--expect a,b] [--ui] [--flow NAME]`** prints the block in five parts: ticket and session, verifier and verdict (the verdict is in the opening lines), checks done, proof, gaps. The predefined list is `--expect` or `verification.checks`. A listed check with no result is a gap, "not done", never "passed". An exception, such as zero tests allowed, is named. With `--ui` the browser check is expected; when the flow (`--flow`, else `flow.use`) switches its `ui-check` step off, the gap says "switched off by the flow configuration" (H-059). Every PR that `ship pr` opens carries this block.
- **`comment <lane>`** posts the same block on the ticket, so the comment and the PR agree. Every result belongs to the lane's commit, so after a fix only results for the new head count.
- **`remarks <lane>`** reacts to the lane's verdict (H-058, D15, D37-VERIFICATION-6). "Passed with remarks" never merges. With `remarks: human` (below `full`) the ticket goes to needs-review (exit 76). With `remarks: fix` (`full`) each call allows one fix round, up to `remarks_max_fix_rounds` (default 3); each round's verdict must come from a validator session not used in an earlier round (exit 65 otherwise). After the last round the ticket goes to needs-review. The verdict gate of `loop merge`, `ship pr` and `ship merge` enforces both rules: a lane handed to a human never merges by itself, and a pass from a validator used in a round does not count.
- **`reviews <lane>`** handles external review on the lane's PR (H-061 to H-063, D37-VERIFICATION-5). `external_review` is `react` (default), `ask` or `ignore`. It reads the PR's reviews and PR comments; inline code comments and the reviewer wait of D44 and D45 are not built yet. Only a trusted author is acted on: write access (the H-008 check) or a login in `external_review_bots`. Anyone else is recorded in the ticket thread and not applied. `react` hands the trusted comments, inside the untrusted fence, to the flow's `review-comments` step; with no such step, or a profile without push, it acts as `ask`: the comments go to the ticket, the human is asked to look at them or ignore them, and the ticket goes to needs-review (exit 76).

## Stops

`bin/harness state <run-dir> stop [--type soft:step|soft:task|soft:ticket] [--ticket ID]... [reason]` records a soft stop (H-086, D25, D25a). The default is `soft:step`.

- **`soft:step`** lets the current step finish. No new step and no new ticket begins, and no merge runs.
- **`soft:task`** works the same in the engine. Its stop text asks the session to stop after its current task inside the step.
- **`soft:ticket`** lets each ticket that began before the stop run to its end: its next steps may begin, their sessions launch, and its lane merges. No new ticket begins. With `--ticket`, only the named tickets go on, and the other tickets get `soft:step`.
- **The newest stop is in force** until `state <run-dir> resume`. While the STOP file exists the run is at least as strict as `soft:step`.
- **Stop text.** The verb prints the stop id and the variant's standard text. It does not deliver a soft stop: send it with `session deliver <name> --text "<text>" --id <stop id>`.
- **Own message.** `--message TEXT` works with every variant (H-085, D37-LIFECYCLE-5). The text is added word for word after the standard line, as one line (line breaks become spaces), and is written once to the run ledger (`own_message`). The STOP file uses the standard text only.

### Hard stops

`bin/harness state <run-dir> stop --type hard:message|hard:now [--message TEXT] [--service-down] [reason]` records a hard stop and acts on it at once (H-087, D25). A hard stop lets nothing new start and may force-close sessions. A force-close targets only the exact process ID recorded for the session, and that process must still carry the session ID (H-103, S8-27).

- **`hard:now`** sends no message. The engine first writes one record per open session of the run to `<run>/stops/<stop id>/<name>.json` (S8-20b), then force-closes each one: SIGTERM, SIGKILL after 2 seconds, then an existence check of up to 10 seconds. An own message is not sent; the output says so in one line, and the ledger keeps it.
- **`hard:message`** (the hard default) sends the hard stop line, plus the own message, to every open session of the run through `session deliver`. With `stop.hard_message.force_send` (default `true`) a queued message gets the runtime's send-now chord (D37-LIFECYCLE-4); with `false` it waits in the queue. The wait `stop.hard_message.wait_seconds` (default 120) starts when the stop is issued. A session is parked when the hook log shows a `Stop` event for it from the last poll before its transcript showed the stop message on; it is then closed the normal way. A session is marked closed only when its process is proven gone. The session that runs the stop (`HO_SESSION_NAME`) is not closed by it; the output names it as `self`. A session whose process is gone counts as stopped. A session not parked when the wait ends is escalated: one `hard-stop-escalated` ledger line, one record, then the force-close of `hard:now`. The output names it (D25c, D37-LIFECYCLE-6).
- **`--service-down`** (hard:message only): the caller knows that the service cannot be reached (D22). No message is sent, and the stop acts as `hard:now` at once.
- **Step gate.** `state <run-dir> begin --ticket T --step S` asks before a step begins: exit 0 and one `step-begin` ledger line, or 75 when a stop lets nothing new start. An unknown stop state also gives 75. An ended run (its newest `run-end` line is newer than its newest `resume`) also gives 75 here, for a worker or heavy slot and for `loop merge`, until `state <run> resume`. A ticket counts as begun when a `step-begin` line for it, the launch of a session with `--ticket` for it, or its intake `pickup` line comes before the stop.
- `state <run-dir> stop-state` prints the stop in force as one JSON line.

## End of run and standby

`bin/harness lifecycle <run-dir> check` decides what the run does now, acts on it, and prints the decision as the first line (H-079 to H-082, S8-20a, D37-LIFECYCLE-3). The decision is worked out again at every call. Only a run end stays, until a resume.

- **`work`**: a ticket is ready or in progress.
- **`stopping`**: a soft stop is in force, and work it allows still runs. Nothing is closed.
- **`wait-review`**: every remaining ticket waits on review. The worker, validator and question sessions close. The orchestrator and the watcher wait, and nothing is sent to them.
- **`wait-blocked`**: only human-blocked tickets remain. The same as `wait-review`, with no nudges.
- **`standby`**: all tickets are done and standby is on. The finished sessions close. The orchestrator and the watcher keep running, and no other session starts.
- **`end`**: all tickets are done and standby is off, or only human-blocked tickets remain with `on_only_human_blocked` set to `end`, or a soft stop has nothing left to finish. One `run-end` line goes to the ledger, and every session of the run closes. The calling session is never closed by itself; the output names it as `self <name>`.
- **`ended`**: the run ended earlier. A session that could not be closed at the run end (busy, or its terminal could not be reached) is tried again at every later call.
- **`unknown`** (exit 2): the stop state or the ticket queue cannot be read, the local ticket folder does not exist, or a ticket of the queue is in none of the five states while the decision would be `end`, `standby`, `wait-review` or `wait-blocked`, and nothing changes. With such a ticket, `work`, `stopping` and the end that a stop asks for still go on, with a notice that names the ticket. On GitHub that last case is an open issue with a harness label (`<prefix>:...`) but no state label; an issue with no harness label is not a ticket.

`lifecycle <run-dir> done <name>` records that a session's task ended and closes it (H-081). It refuses the orchestrator and the watcher, which close only at run end, and a session of another run.

Every close goes through `session close`, by the exact process, over this run's registry only. The run keeps no ticket list of its own: its tickets are those of the queue (`tickets ids <state>`, the folder `<project>/.harness/tickets` unless `HO_TICKETS_DIR` is set).

Settings (OPEN-9): `run.standby` (`true` or `false`, default `false`), overridden for one run by `run new --standby on|off`. `run.on_only_human_blocked` (`wait` or `end`, default `wait`). Both are fixed in `<run>/lifecycle.json` at run start and written once to the ledger as `run-settings`. Any other value is a config error (exit 78).

## Permission prompts (H-052, D37-AUTONOMY-1, D37-AUTONOMY-2)

The permission mode stays your own setting: `session.permissions` in the user config (`bypass`, the shipped default, `auto`, `acceptEdits` or `dontAsk`). The plugin passes it to each session and enforces nothing else. Under `bypass` prompts normally do not appear.

`session.permission_prompts` decides what the harness does when a permission prompt is on a session's screen (screen class `permission`). It never changes the mode and adds no deny list.

- `off` (the default): no answer. One owner-action line goes to the run ledger, once per screen.
- `analyse`: the main runtime reads the prompt with no tools, from an empty folder, with the screen inside an untrusted fence (`templates/permission-prompt.md`). If it answers `{"acceptable": true}`, the harness reads the screen again and, when it is unchanged, presses the runtime's accept-once key (`permission_prompt.accept_once` in the runtime profile) once and writes a `permission-answer` ledger line. It never picks "always allow". Doubt, a failed analysis, a changed screen or a runtime without the key escalates as with `off`. There is no always-accept value.

The setting is read once at run start into `<run>/settings.json`. `bin/harness screen <run-dir> permission <session>` reads the screen and reacts; `screen ... watch` does the same when it sees the prompt. The setting is a recorded field of D37-FLOW-8: a committed config that moves it from `off` to `analyse` stops the next run start. The shipped screen pattern file has no permission shape yet, so until it gets one, real prompts read as other screen text; the tests use a synthetic pattern.

## Autonomy profiles

An autonomy profile holds gates and permissions only; the steps stay in the flow config (D12, D37-FLOW-3). Four ready-made profiles ship in `autonomy/`. None of them deploys to production, and none names a stage environment.

- `safe` (the default): plan, execution, review and verification run on this machine. No push, no PR and no merge, not even a local integration merge. The ticket ends in needs-review.
- `gated`: a human approves the readiness point, the plan and the PR. It pushes, opens a draft PR and stops. No merge.
- `draft-pr`: no human gates. It pushes, opens a draft PR and stops. A human marks it ready and merges.
- `full`: no human gates. It pushes, opens the PR, marks it ready and merges only when every mechanical condition holds (S8-08b). Then it runs the project's post-merge steps.
- `custom`: set `autonomy.profile` to `custom` and every field in `autonomy.custom`, at your own risk. Only here may `merge` be `classifier`, and only here may `deploy_production` be true. A missing or unknown field is refused.

Fields: `gates` (`{<point>: "auto" | "human"}`; a point is a flow step id or one of `start`, `readiness`, `pr`, `merge`), `push`, `pr` (`none`, `draft`, `ready`), `pr_open` (`none`, `after-validator` or a step id), `merge` (`never`, `always`, `classifier`), `post_merge`, `deploy_production`, `remarks` (`human`, `fix`) and `allow_zero_tests`. Select a profile with `autonomy.profile` in the project or user config. A config with no profile but with the 0.6.0 key `guardrails.never_push` gets `safe` for true and `draft-pr` for false. A project config that sets `guardrails.never_push: true` and no profile of its own gets `safe`, whatever profile the user config names (#110). `bin/harness autonomy migrate <0.6.0-config>` prints the profile an old config file becomes.

The engine checks the profile at every step boundary and before push, PR, merge and deploy, not per tool call (S8-08a): `bin/harness autonomy <run-dir> check <action>`, with the actions `start`, `step --step <id>`, `push`, `pr`, `pr-ready`, `merge`, `post-merge` and `deploy`. Exit 0 allows it, 76 means it waits for a human, 77 means the profile does not allow it, and 78 is a config error. Each check writes one ledger line. The profile is read at the first check of a run and kept in `<run>/autonomy.json`, so a config change during a run counts from the next run (H-036).

- **Human gates.** `check step --step <id> --for <ticket>` returns 76 at a point the profile marks `human`. `autonomy <run-dir> approve <ticket> <point>` records a human's approval; it is refused from inside a harness session. The `merge` point is also checked by `check merge`, and the `pr` point by `check pr-ready`: the draft PR opens, and a human approves it before it is marked ready.
- **Merge into the target.** `check merge --facts <file>` reads the facts as JSON: `validator` (`passed`), `tests.total` and `tests.failed`, `ci` (`green`), `open_questions` and `paths`. Every condition must hold, and a missing or unreadable fact fails. A changed path that matches a pattern in `autonomy.always_human_paths` refuses the merge; the project and user lists count together. `merge: classifier` waits for a human, because the classifier is not built yet.
- **Local integration merge.** `loop merge` asks the profile first. It refuses when the profile allows no push and no merge, as `safe` does. Other profiles keep the loop's own checks. A config with no profile gets `safe`, so a test or project that merges locally must select a profile, for example `"autonomy": {"profile": "draft-pr"}`.
- **Deploy.** Allowed only when the profile has `deploy_production: true` and the project config names a deployment (`deploy.use`) (H-049).
- **Ticket end.** `autonomy <run-dir> end <ticket>` sets the ticket to needs-review when the profile never merges. Under a profile that merges, the ticket waits for the confirmed merge. With local tickets and `HO_TICKETS_DIR` unset, it acts on `<run's project>/.harness/tickets`, wherever it is called from, as intake and lifecycle do.
- The setup question for the profile is `/harness:config`, and the record of the approved profile with its comparison at run start is in Config and run state. Not built here: the push and PR steps that call these checks (#59), remarks and external review (#60), and the reaction to a ticket that is not ready (#51).

## Notifications (H-115 to H-123, D36, S8-28a)

Channels are optional; with none set, questions and answers stay in the tracker, which is always the source of truth. Each channel is one entry under `notify.channels.<label>` with a `preset` (`telegram`, `slack` or `gmail`) and a route:

- `"via": "command", "argv": [...]`: only in the user config. The engine runs `<argv> send` (text on stdin, `HO_NOTIFY_KIND`, `HO_NOTIFY_TICKET`, `HO_NOTIFY_EVENT`, `HO_NOTIFY_REPLY_TO`; first stdout line is the message ref), `<argv> read_replies` (JSON lines `{id, reply_to, sender, text, authenticated}`) and `<argv> check`, with no shell and 20 s at most. Tokens stay with that program. A project config that holds a channel command is refused at start (D37-FLOW-8).
- `"via": "mcp", "mcp": "<connector>"`: allowed in the project config too. The engine queues each message in `<run>/notify/outbox.jsonl`; the session sends it with the connector and reports `harness notify <run> sent <id> <ref>` or `failed <id>`, and passes replies in with `harness notify <run> inbox <label> <file>`.

Settings: `notify.use` (active labels; default all), `notify.priority` (default the order of setup), `notify.questions` (labels for questions; default all active), `notify.events.<event>` (default true) for `question`, `blocked`, `taken`, `done`, `run-ended`, `limit-pause`, `orchestrator-down`. A message goes to each selected channel; a failed send goes to the next unselected channel by priority.

`harness tickets ask` mirrors the exact numbered lines once the tracker holds them. The intake tick reads replies: the first reply to a question is recorded on the ticket with `tickets answer`, with the author mapped through `identities` in the user config (`senders.telegram`, `senders.slack`, or `emails` for an authenticated Gmail sender); exactly one entry must match, or the sender is unmapped. The normal answer rules then apply it or move the ticket to needs-review. A later reply gets the tracker link and is never applied. A message that answers no question is dropped. `harness notify check` is the read-only connections check before the build; it lists the owner actions from `templates/notify-presets.json` for a failed channel.

## Feedback (H-140, D43, D60)

`/harness:feedback` files a problem with the harness as one issue in the plugin's own repository (the manifest `homepage`), with no labels. The person describes the problem in their own words. The command file (`commands/feedback.md`) runs two engine verbs:

- `bin/harness feedback preview <description-file>` builds the issue and sends nothing; with a GitHub ticket source it only reads ticket counts. It prints the full text, then a fixed end marker line, then a `DRAFT <id>` line and a `CODE <code>` line. The code is the first 16 hex digits of the SHA-256 of the exact title and body. The text says which repository gets the issue and that it is filed under the person's own GitHub login.
- `bin/harness feedback send --draft <id> --code <code> --yes` sends exactly the shown draft with `gh issue create`. Without `--yes`, with a wrong code or with a changed draft, it sends nothing (exit 65).
- Drafts (issue #124): a draft lives only in the private draft folder `~/.claude/harness/feedback-drafts` (mode 700; `HO_USER_DIR` moves it) under an opaque random id. `send` takes that id, or a path whose real place is a draft right inside that folder; a link or anything outside is refused (exit 65) before anything is read or removed, and cleanup removes only inside the folder. The control lines come only after the end marker, and a description that holds the marker line is refused (exit 64), so description text cannot imitate them. Drafts older than 7 days are removed at the next preview.

The technical context is built from named fields only, and nothing outside this list is copied: the plugin version (a version-shaped manifest value, else `unknown`), the runtime label and version (`runtime.main` only when the plugin ships a runtime of that name, else `unknown`; the version is the first version-shaped word of `<command> --version`, 5 s limit; the command is found and guarded as a session launch finds it, a binary from the project or a worktree is never run, and the probe gets only the system folders and the runtime's own folder on PATH), the operating system (`uname -s`, `-r` and `-m`, each checked against a fixed shape, else `unknown`; never the host name) and a summary of the newest stamped run of the project. The summary holds only: stopped, not stopped or stop state unknown (read as the engine reads it, STOP file first, without writing anything), the number of ledger events, session roles launched (`orchestrator`, `worker`, `validator`, anything else counted as `other`), ticket counts per state, and the engine's own failure event kinds from a fixed list (`deliver-failed`, `marker-foreign`, `owner-action`, `pretrust-refused`, `session-boot-failed`, `session-close-failed`, `session-close-refused`, `session-close-timeout`, `session-dead`, `session-launch-failed`, `unreadable`) with counts. No ledger value, ticket text or runtime output is copied. These are all the fields; the context has no verb or exit code field, because no harness record holds them.

The person's description is sent as written: D60 (owner decision 2026-11-27 on #92). The harness does not scrub it: the person is responsible for what they paste, so a path, a token or a name they type reaches the issue. The preview shows the full text, description and context, exactly as it will be sent, and nothing is sent without the exact `--yes` and the confirm code of that text. The issue title is `Harness feedback: ` plus the first non-blank line of the description, cut at 70 characters. A description over 60000 bytes is refused (exit 64), because the tracker limits the issue body.

The issue goes to `github.com/<owner>/<repo>` even when `GH_HOST` names another server. A linked `.harness/runs` folder is followed when the last run is looked up.

`send` checks the context part again: from the last `---` and context header on, every line must be one of the fixed fields above with its fixed shape (exit 65 otherwise, naming only what is wrong). Any probe that fails gives `unknown`, so a broken config or no run still gives a report. The preview writes nothing in the run folder.

## Field notes for contributors

`plugins/harness/docs/FIELD-NOTES.md` records what the 0.6.0 engine did in two long unattended runs.
You do not need to read it before every change.
Read the matching section before you change one of these areas, and when you write tests for it:

- session liveness, recovery, closing sessions — section A
- sending instructions to a session — section B
- merge, validation, git operations — section C
- tickets, labels, run state files — section D
- more than one worker, heavy work, Docker — section E
- subscription limits, the limit banner, pause and resume — section F
- worker cap defaults, usage history, timeouts — section G
- any detector, probe or gate that reads a screen, a log or an exit code — section I

Each record names the requirement or design decision it relates to, or says that none fits.
A record is covered when a test fails without the fix.
