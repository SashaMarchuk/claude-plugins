# Harness Orchestrator

This branch holds the stable-beta rebuild of the harness plugin. The 0.6.0 engine is removed here, and the new engine is not usable yet. Parts of the old engine come back only from the reuse list in the design, each with a behaviour test shown failing first. The released 0.6.0 code stays on `main`.

## Engine entry point

The engine has one entry script: `bin/harness <verb> [args]`.
Current verbs are `version`, `help`, `selftest`, `config`, `run`, `state`, `tickets`, `session`, `slot`, `flow`, `loop`, `screen` and `lifecycle`.
Run `bin/harness help` for the list.

## Ticket queue

`bin/harness tickets <verb>` runs the ticket queue. Run `bin/harness tickets help` for the verbs.
It has two backends: GitHub issues with one `<prefix>:<state>` label, and local files in a folder.
The five states are `ready`, `in-progress`, `blocked`, `needs-review` and `done`.
Every state change leaves exactly one state label.
Ticket titles, bodies and comments are printed only inside the untrusted fence.
A report is always a new comment; no comment is edited or deleted.
Settings: `HO_TICKETS_SOURCE` (`local` or `github`), `HO_TICKETS_REPO`, `HO_TICKETS_DIR`, `HO_STATE_PREFIX` (default `harness`), `HO_TICKET_LOCK_WAIT` and `HO_TICKET_LOCK_STALE`.

## Variable names

The new engine's own environment variables use the prefix `HO_` (Harness Orchestrator), for example `HO_HOME`.
It never reads any `HARNESS_*` variable from the 0.6.0 engine.
`bin/harness selftest` fails when a 0.6.0 variable is set or a 0.6.0 engine script is on `PATH`.

## Config and run state

- **Config lookup.** A project value beats a user value, and a user value beats the engine default. The project config is `<project>/.harness/config.json`. The user config is `$HO_USER_DIR/config.json`, by default `~/.claude/harness/config.json`. Only a missing key or `null` falls through to the next layer. Every config file must have `"schemaVersion": 2`; any other file is refused (exit 78) and the message names the file. The templates are in `templates/`.
- **Run stamp.** `bin/harness run new` creates `<project>/.harness/runs/<run-id>/` with a `run.json` stamp. Every `bin/harness state <run-dir> ...` verb checks the stamp first. A folder without a valid stamp, such as a 0.6.0 run, is refused (exit 66) and nothing in it changes.
- **Run ledger.** `ledger.jsonl` in the run folder holds decisions, owner actions, stops, resumes and marker events, one JSON line each. Lines are only appended, under a lock, and every line carries the run ID.
- **Markers.** Each marker file holds the run ID. A marker without this run's ID is ignored and logged once as foreign.
- **STOP file.** `<project>/.harness/STOP` still works. It is recorded in the ledger as the default soft stop, `soft:step` (D25b), also when it appears while a looser stop is in force. A new run and `state ... resume` are refused while it exists. See Stops.

## Sessions

`bin/harness session <run-dir> <verb>` launches, lists and closes sessions of one run.

- **Launch.** `launch --role R --name N --cwd DIR --prompt FILE` (or `--resume SESSION-ID`), with optional `--account A`, `--model "a|b"` and `--ticket ID` (the ticket the session works on; it decides whether a `soft:ticket` stop lets the launch start, and is kept in the record as `ticket`). Roles are `orchestrator`, `watcher`, `worker`, `validator` and `question`. The working folder must be inside the project or a worktree of it. The engine writes a launcher to `<run>/launchers/<name>.sh` and opens it in a terminal. The launcher has a clean PATH, a guarded `cd`, the role's account and a fixed session ID. It tries each model of the chain in turn when a start fails. Each attempt writes its own process ID, so the registry holds the exact process.
- **Registry.** `<run>/sessions/<name>.json` is the one record per session. It holds the run ID, the process ID, the session ID, the role, the account and the terminal handle. A session's identity is its process ID plus its session ID. The terminal handle is used only to reach the session. Handles can be reused: a tmux pane ID after the `ho-harness` server restarts, an iTerm2 window ID after iTerm2 restarts. So the engine tags each pane or tab it opens with a tag made new for each launch and kept in the record as `term_tag`, and with the session ID (tmux pane options `@ho_tag` and `@ho_session_id`, which need tmux 3.0 or later; iTerm2 session variables `user.ho_run`, `user.ho_session` (the tag) and `user.ho_session_id`, which need iTerm2 3.3 or later). It types into, reads or closes a pane or tab only while it carries the run, the tag and the session ID of the record, and it adds a tab to a stored iTerm2 window only while that window holds a session of this run. Before close types anything, the PID file must name the record's run, session ID and process ID, and that process's command line must hold the session ID; otherwise close leaves the session open (exit 70). iTerm2 open finds the new session by value: it reads the window IDs, or the session IDs of the window, before and after the create, inside one `tell`. If not exactly one new ID appears, open tags and closes nothing and fails (exit 70). It tags the new session only while it carries no tag yet. The tag is not the session ID, because `launch --resume <session-id>` starts a new launch with the same session ID. A resume is refused (exit 65) while a record of this run with that session ID is not closed. A record without `term_tag` is left open by close (exit 70). Every iTerm2 call reaches its window by `first window whose id is <id>` and its session by `first session of (tab <k> of <that window>) whose unique ID is <id>`, and checks the tag inside the same `tell`, right before it types, reads or closes.
- **Close.** `close <name>` refuses a record of another run (exit 66). A session whose process is proven gone is only marked closed. When this caller cannot read the process table, or can neither see the session's process nor prove it gone, close changes nothing and exits 71. A `launching` record can be closed once the launch command that wrote it has ended. A live session gets the runtime's exit command typed into its own terminal, and the close counts only when that exact process has ended. A session still busy after `session.close_timeout_seconds` (default 90) is left open (exit 1) and never forced. When the process has ended but its pane or tab no longer carries this launch's tag, the terminal is left alone and the ledger records `session-close-terminal-skipped` with the reason. `list` shows the process that runs now, also after a model fallback. Known limit: close does not clear text already sitting on the session's input line (field note B1); such a close times out and the session stays open. No process is ever matched by name.
- **Deliver.** `deliver <name> (--text T | --file F) [--id ID] [--force-send]` sends one instruction to a running session (H-101, H-099, H-137; design S8-24, D42f, D42g). Every instruction carries a short unique id, made by the engine unless `--id` is given, and the text the session gets starts with `<id>: `. An id is 6-40 characters of `a-z 0-9 -`, checked as one whole value, and is used once per run. The message route goes first: the runtime data's `message.argv`, when it names a command. A message whose outcome is unknown is never typed; a proven failure falls back to typing (H-101). After the command has started, the transcript is read with the same bounded wait in every case. If it shows the id (delivered, queued or dequeued), the result is reported and nothing is typed. A proven failure is one of two cases. Either the command could not start at all: it is missing, not executable, inside the project, or its `#!` line names a missing interpreter. Or it exited non-zero, its process group is gone, and the readable transcript has no record of the id. Only then does the typed route run, with all its checks. A timeout, an exit by a signal, an exit 0 with no proof, or an unreadable transcript is unknown: one `owner-action` line, nothing typed, no retry. A command still running at `delivery.message_timeout_seconds` gets SIGTERM on its own process group, then SIGKILL after `delivery.message_kill_grace_seconds` (default 2); after a non-zero exit, what is left of its group is stopped the same way. The typed route runs only when the engine's screen reader (`lib/screen.sh`) finds no hold on the same capture (no limit notice, trust dialog or password prompt, read with the pattern file of the session's own runtime; a hold gets 0 bytes, no Enter and no chord), and only when the screen shows the runtime's idle input line, empty, with no busy mark. The screen is read, never probed with a key, and nothing is ever typed to wake a session. On the typed route the screen is read fail-closed. Every CSI escape code is stripped first, and a capture that still holds an escape byte reads as unknown. The input line is a prompt-prefix line right below a rule line; more than one such line reads as a draft. The box ends at the last line of the whole capture below it that equals the opening frame line byte for byte, with no line cap; a rule line of another width or character is the person's text, and with no equal line the box is not closed and reads as a draft. The box is empty only if the input line holds no text (dim suggested text aside) and every other line inside the box is blank. Any other text inside it, a rule line included, is a draft, and a draft gets 0 bytes, `--force-send` included. A busy session, a dialog or any screen the runtime data does not describe gets nothing typed either, and the instruction is reported as not delivered. The text is typed without Enter and the screen is read again. The lines above the box go to the screen reader once more, so a hold that appears above a box with typed text is still seen. If those lines are all blank, the reader has nothing to judge and the screen reads as unknown, so nothing is typed; this fails safe on purpose. On a hold, or a busy mark on a delivery that is not a forced stop, no Enter is sent, and one `owner-action` line says that the text sits typed on the input line; that line holds a fixed phrase and the class word only, never screen text. Otherwise Enter goes only when the line holds exactly the typed text. Dim text after the prompt is suggested text and counts as empty on tmux; iTerm2 keeps no colours, so there it counts as a draft. Text of at most `terminal.typed_max_bytes` bytes (default 800, at most 1000, counted in bytes) inside the safe character set is typed as it is. Any other text goes into `<run>/messages/<id>.txt` (mode 600, written to a temp file and linked into place), and a short line that names the file is typed instead. An instruction counts as delivered only when the session's transcript records a user turn whose own text carries the id, a queued-command record that carries it, or a reply of the session that names it. The id is matched as a literal whole word: no ASCII letter, digit, `_`, `.`, `-` or character outside ASCII may touch it, and an id glued to a copy of itself does not count. A tool result never counts, nor a user record marked `isMeta`, `isCompactSummary` or `isSidechain`, and any other transcript growth only shows the session is alive. Without a readable transcript nothing is sent. The engine does not send an id a second time by itself; a caller that sends the same instruction again uses a new id. `--force-send` is for the stop message of a hard stop only (D37-LIFECYCLE-4): the text may then be typed into a busy session, and once the transcript shows it queued, the runtime data's send-now chord (`force_send.bytes`: numbers 1-31, never 10 or 13) is sent once, while the transcript shows it queued (whatever the message command's exit status) and only when the same screen gate as typing is open (an empty input line or a busy session; never on a hold, a draft or an unknown screen), when the runtime is at least `force_send.min_version`. The version comes from the runtime path the launch checked and recorded (`runtime_path`), never from a PATH lookup. Exit 0 delivered, 1 not delivered; the ledger records each step under the id. Every program delivery runs (the message command and the runtime's version check) gets a fixed PATH: `/usr/bin:/bin:/usr/sbin:/sbin` and the program's own folder, never a project folder and never the caller's PATH. So a runtime whose interpreter lies outside the system folders and the runtime's own folder cannot be version-checked; its chord is then skipped and logged. Delivery safety settings are read from the user config only; a project config that sets one, to any value including `false`, is refused with exit 65, and a value that is not a whole JSON number in range exits 78: `delivery.wait_seconds` (30, 2 to 3600), `delivery.message_timeout_seconds` (30, 1 to 600), `delivery.message_kill_grace_seconds` (2, 0 to 30) and `terminal.typed_max_bytes` (800, 300 to 1000). `terminal.enter_delay_seconds` (2, a JSON number, whole, from 0 to 10; any other value, a string included, exits 78) is a shared terminal setting that graceful close also uses, so it may stay in the project config. Tools that read the runtime's output (the version parse and compare) run as `/usr/bin/awk`, and the version check itself runs in its own process group with a limit of 5 s; on a timeout the version is unknown and no chord is sent. The session's transcript folder (`transcript_root`) is worked out by the launcher in the session's own folder and environment and copied into the record at launch, so delivery never runs the account command; delivery reads it only from the record, never from the launcher's note. Delivery refuses a recorded folder inside the project or a worktree, and a transcript reached through a linked folder below the recorded folder, and uses a cached transcript path only after resolving it (`..` segments and folder links), and only when it lies inside the resolved folder and its file name is `<session-id>.jsonl` or a folder on its path is the session ID.
- **Proof.** `proof <name> <id>` runs the delivery check alone, for an instruction the caller sent itself, for example an orchestrator session that used the runtime's own message tool. It prints `delivered <how>`, `queued` or `none`, and exits 0 only when delivered.
- **Runtime.** The launch command, its arguments and the exit command come from the runtime profile named by `runtime.main` (see Runtime profiles). `runtime.main` must be set; the project template sets it. The same file holds the delivery data: `message.argv` (null in `claude-code.json`, because no script interface for messages between sessions is documented), where the transcript is and which records prove delivery, what the idle input line looks like, and the send-now chord.
- **Accounts.** Accounts are read from the user config only: `accounts.roles.<role>` (or `accounts.roles.default`) names an account, and `accounts.list.<name>.env_command` prints `KEY=VALUE` lines for it. A launch fails when `--account` differs from the role's account, or when the account is unknown or its command fails.
- **Trust boundary.** The permission mode `session.permissions` is read only from the user config or the shipped default; a project config that sets it refuses the launch (exit 65) until the local approval record of D37-FLOW-8 exists, so move it to the user config. The runtime command found on PATH must not be, or link to, a file inside the project, a configured `repos[].worktrees_dir` or a git worktree of the project; otherwise the launch is refused (exit 65) and names the path.
- **Terminal.** `terminal.app` is `auto`, `iterm2` or `tmux`. With tmux the harness uses its own server (`tmux -L ho-harness`) and one tmux session per run, named `ho-<run-id>`; attach with `tmux -L ho-harness attach -t ho-<run-id>`. Other settings: `session.permissions` (user config only, default `bypass`), `session.boot_timeout_seconds` (120), `session.boot_grace_seconds` (45), `session.fatal_hold_seconds` (30), `terminal.enter_delay_seconds` (2, a JSON number, whole, from 0 to 10), and `models.<role>` for the default chain. The delivery settings are listed under Deliver.

## Liveness

`bin/harness session <run-dir> status [name]` reports facts, one JSON line per session; the orchestrator judges them (D20).

- **Verdicts.** `working`: the recorded process is alive and its command line holds the session ID. `starting`: no session process runs, but the launch command or the launcher of this launch is alive (a launch waiting for a slot, an account command, a model fallback). `dead`: every recorded process of the session is proven gone (the launch command, the launcher and the session process); a `running` record then turns `dead` once, with one `session-dead` ledger line. `closed`. `unknown`: the record or the process table cannot be read, or a process can neither be seen nor proven gone; this is never reported as `dead`.
- **Proof of an end.** The age of a record is never evidence. The launch records its own PID and start time (`launch_pid`, `launch_start`) and the launcher writes `<name>.launcher` before anything slow, so a reused PID never counts. A process is gone only when `ps` shows that PID with another start time (or without the session ID), or when `ps` shows nothing and the kernel answers "No such process" to `kill -0`; a probe that succeeds or is refused gives `unknown`. A launcher that ends writes `<name>.ended` (or `<name>.failed` when it gives up), which proves that no session of that launch runs. So a caller whose view of the process table is narrower than the sessions' (a sandbox) reads `unknown`, never `dead`. On Linux the record names its PID namespace, and a caller in another namespace reads `unknown`.
- **Silence is not death.** A session whose transcript has not changed for hours still reads `working` while its process lives. The transcript age is a number in the report and never changes the verdict. There is no stall rule.
- **Transcript and screen.** `session <run-dir> read <name> transcript|screen [--lines N]` prints the tail of the session's transcript or screen inside an untrusted fence. The transcript is found by the recorded session ID under the root the runtime file names (`transcript` in `runtimes/<runtime>.json`); the launcher works the root out in the session's own folder and environment (account variables applied, so an account may set it from `$PWD` or set `HOME`) and the launch records it as `transcript_root`; the account command runs once in the launch command (its check) and once in the launcher. The screen is read only while the pane or tab carries this launch's tag and the session ID. A line inside that names the fence (`begin` or `end`, then `session`, in any case) gets a `[session-text]` prefix, so session text cannot close the fence.
- **No typing.** Nothing in the engine types into a session to wake it (H-099). The only typed text is the exit command of a graceful close.

## Limits and slots

The engine enforces the worker cap, one heavy job at a time and the stage limits (H-104, H-105, H-107, design D26 and D26a).

- **Worker cap.** `bin/harness run new --workers N` sets it for the run. Otherwise `limits.workers` from the config is used, and the default is 1. The minimum is 1, and no maximum is shipped. The limits are fixed in `<run>/limits.json` when the run starts.
- **Worker slots.** `session launch --role worker` takes a slot under one lock before anything is opened. When the cap is reached, the launch exits 73 and writes nothing, or it waits up to `--slot-wait SECONDS`. A stop recorded while the launch waits ends the wait with exit 75, and nothing is opened. A stopped run takes no new worker slot, except for a ticket that a `soft:ticket` stop lets finish. A soft stop still gives a heavy or stage slot to a session that already runs, so its step can finish (D25a). An unknown stop state refuses every kind: `acquire` gets 75 with or without `--wait`, and the stop is read under the lock at every try. A heavy or stage `acquire --wait` also ends with 65 or 66 when its session is closed, ends or is gone during the wait; the holder is checked again under the lock at every try, so nothing is recorded for it. Close, or a session that reads `dead` or `closed`, gives the slot back; before a `dead` holder's slot is freed its close flag is written, so a launcher that has not started its session starts nothing. A failed launch gives it back only when its session reads `dead`; a session that came up anyway holds the slot until it is closed or ends. A holder that reads `unknown` keeps its slot: a record from older code, an unreadable record, a launch command that hangs. The owner's way out is `slot <run-dir> release worker --holder NAME --force`. It needs a terminal where the session name is typed, writes the close flag and a `slot-force-released` ledger line, and refuses a holder that reads `working` or `starting`, before the prompt and again after the answer. With no terminal it exits 65. The terminal check stops accidents, not a script: a program that opens a terminal passes it, so it is a speed bump, not a security boundary (D37-FLOW-8a). Use it only when you know the session's process has ended. If that process is in fact still alive, the run then has one worker more than the cap, and the close flag left behind stops that session's model fallback (a later `session close` still works). Stop a hanging launch command by its exact PID (`launch_pid` in the record) first; the slot then frees by itself.
- **Heavy work.** `bin/harness slot <run-dir> acquire heavy --holder NAME --op TYPE [--wait S]` and `release heavy --holder NAME`. The six shipped types are in `limits/heavy-ops.json`. `slot <run-dir> heavy-add TYPE REASON` adds a type for one run; it takes a name only and never changes a limit (`limits.heavy`, default 1).
- **Stages.** `acquire stage:<id>` and `release stage:<id>`; `browser` and every other stage default to 1 (`limits.stages.<id>`). A session that needs a stage slot and the heavy slot takes the stage slot first.
- `slot <run-dir> list` shows the held slots and `slot <run-dir> limits` the limits. No free-memory check is made (S8-21).

## Flows

A flow config is a folder with `flow.json` and one prompt file per step. It holds the steps, their order and their runners (S8-15). Gates and permissions belong to the autonomy profile, a separate file: a `flow.json` that sets one of its keys (`gates`, `push`, `pr`, `merge` and the like) is refused, and no flow verb writes outside the flow folder (D37-FLOW-3).

Two ready-made flows ("flow profiles") ship in `flows/`: `gsd` and `basic`. Both give the default cycle (H-064): classification, discussion (grilling) only when classification finds open questions, planning, execution, code review, verification, UI check and shipping, in that order. `basic` writes every step out as a plain prompt and needs no flow system. `gsd` runs the middle steps through GSD, which must be installed; classification and shipping stay harness steps. A project's own flows live in `<project>/.harness/flows/<name>/`. A project flow may not have the name of a shipped flow, and its folder must stay inside the project.

- `bin/harness flow list` prints the shipped and the project flows; a missing flows folder stops with exit 78. `flow check <flow>` checks the flow file, every step prompt and the role prompts. `flow steps <flow>` prints the steps that are on, one per line: number, id, `always` or `questions`, title.
- `bin/harness flow render <flow> <role> [--step <id>] [--set NAME VALUE]... [--file NAME PATH]...` prints a role prompt. The roles are `worker` (one step; needs `--step`) and `validator`. The role prompts are in `prompts/` and are the same for every flow.
- Placeholders have the form `@NAME@`. The engine fills `FLOW_NAME`, `FLOW_STEP_LIST`, `STEP_ID`, `STEP_TITLE` and `STEP_TEXT`. The caller sets `RUN_ID`, `TICKET_ID`, `TICKET_TEXT`, `BRANCH`, `BASE`, `WORKDIR`, `STEP_RESULT_FILE` and `VERDICT_FILE`. `TICKET_TEXT` must be exactly what `harness tickets fence <id>` prints for ticket `TICKET_ID`; anything else is refused (exit 65). `TICKET_TEXT` is the only value that may span lines. Any other value that holds a line break, a CR, another byte below 0x20 except tab, DEL, a Unicode line or paragraph separator (U+0085, U+2028, U+2029) or a bidi control (U+202A to U+202E, U+2066 to U+2069) is refused (exit 65). `TICKET_ID` must be a number of at most 9 digits (exit 65 otherwise). A placeholder with no value or an empty value fails the render (exit 65), and nothing is printed. Values must be UTF-8 text (anything else is refused with exit 65, never changed; `render` uses `iconv` to check this). They are inserted as they are and never scanned again, so ticket text that quotes a placeholder is safe. Each value reaches jq through a temp file, so a large ticket is no problem.
- There is no default flow. A missing or broken flow (also an empty `flow.json`) stops with exit 78 and names the flow. Engine code (`bin/`, `lib/`, `prompts/`) names no flow system, vendor, runtime or model; such names live only in data.
- Selecting the flow for a project comes later (H-069 to H-072). `HO_FLOWS_DIR` points at another folder of ready-made flows.

### Editing steps (H-066)

Edit the step list in `flow.json`. The order of the list is the order of the run.

- **Reorder** by moving a step in the list. Code review may come before shipping, where the PR opens.
- **Add** a step with its own `id`, `title`, `when` and `prompt` file, anywhere in an own flow: a version bump, a connection check, a test audit before or after code review.
- **Switch off** a step with `"enabled": false`, for example code review when a review bot reviews every PR. It leaves `flow steps`, the numbering and the step list in every prompt, and it cannot be rendered. A flow with every step off is refused.
- **Name a runner** with `"runtime": "<label>"`, a runtime profile. A step without one uses `runtime.main`.
- `"kind": "review"` marks a review-type step (code review, UI review, a second opinion). `"skills": [...]` and `"agents": [...]` name the skills and agents a step uses; the start check checks them. A step may hold only these documented keys; `flow check` refuses any other key by name. The same holds for the top level of `flow.json` and for `system`. `"install": {"<skill>": "<install step>"}` gives their install steps.

### A chosen flow system (H-067, D17, D37-FLOW-2)

A flow with `"source": "system"` points to a chosen flow system, for example GSD. Its `system` object names the system and its `link`, its `install` step, the `skills` the flow uses from it, and `steps`: the ids of the steps the system owns. The system itself is linked, never copied into the repository (H-073). Any system name is accepted (H-068).

The chosen system owns its steps. They form one block, in the order of `system.steps`. Harness extra steps go only before or after that block. Each of these stops with exit 78, names the step and names the route: a step placed inside the block, a system step out of order, a system step switched off, and a flow with `"source": "own"` that also has a `system`. The harness never merges two step lists and never moves or drops a step by itself. A system step may still name its runner.

The route is an own flow: `bin/harness flow copy <flow> <new-name>` copies any flow into `<project>/.harness/flows/<new-name>/` as an own flow (`"source": "own"`, `"copied_from": "<flow>"`). The system's skills, agents and install step stay on the steps it owned, so the start check still checks them. Copy never overwrites a project flow, refuses the name of a shipped flow and writes nothing else.

## Runtime profiles

A runtime profile is one data file per tool (D31, D37-RUNTIME-2). Two ship in `runtimes/`: `claude-code` and `codex`. A profile is read from `<user dir>/runtimes/<label>.json` first, then from the plugin's `runtimes/`. A project can never add one, because a profile holds launch lines (D37-FLOW-8). A profile lists its `modes` (`interactive`, `noninteractive`), the interactive launch (`argv`), the launch without a terminal (`noninteractive`), the `permissions` and `sandbox` flags, the `skill_call` form, `config_dir`, `session_log`, `limits`, `capabilities`, the login `check`, the `skill_paths` patterns and the `install` step.

- `bin/harness flow plan <flow>` prints each step that is on, with its runtime, mode, owner (`harness` or `system`), a note and its launch line, all from profile data: `<n> TAB <id> TAB <when> TAB <title> TAB <runtime> TAB <mode> TAB <owner> TAB <note> TAB <launch>`.
- **Mode (D30, H-102).** A step runs interactively in a terminal when its runtime can. Codex has no interactive mode in this beta, so every step on Codex runs through `codex exec`. A review step runs there with the read-only sandbox. Any other step on Codex, such as execution, runs only where the flow names Codex for it and is marked `experimental` (untested until a comparison run gives the same result).
- **Start check (H-073, H-078, D37-RUNTIME-3).** `bin/harness flow preflight <flow>` checks that every runtime the flow uses is on `PATH` (outside the project) and logged in, and that every skill and agent a step names, and for a system's steps every skill and agent of the system (`system.agents`), is installed for that step's runtime. Config folders and `{home}` follow the worker account: its variables win, then the environment, then the profile default under the account's `HOME` (or the caller's when the account sets none), as in a launched session. Agents are found through the profile's `agent_paths`; a runtime whose profile has none cannot show an agent, so the agent counts as missing. The login check runs in its own process group with stdin from `/dev/null`, the clean PATH and a time limit of `check.timeout_seconds` (a whole number from 1 to 600, default 20). On a timeout the whole group gets TERM, then KILL after 2 s, by its exact group ID, under the worker role's account; a missing command, a non-zero exit, an output without a login and no answer in time all count as missing. The whole check runs first; then every missing item is printed in one list with its install step, and the exit is 69. Install text from a project flow is marked as not checked. Nothing is ever installed. Experimental steps are named in the output.
- Running a step without a terminal is not wired into `session launch` yet; the run loop comes later.

## Run loop and merge

`bin/harness loop <run-dir> <verb>` takes one ticket's lane to a local merge that the engine checks (H-055, H-046). It merges only into the run's local integration branch and never pushes.

- **Integration branch.** `integration --repo R --base B --worktree W` creates the branch `ho/<run-id>` at base `B` and checks it out in the new worktree `W`. Each run has one. `<run>/integration.json` keeps the last confirmed tip.
- **Completion signal.** `ready <lane> --worktree W [--ticket ID]` accepts a lane only when the tip of its branch is a `finalize(<lane>):` commit and its tree is clean. Nothing else counts as done. It records that commit, and the session ID of the session that called it (the lane's worker), and prints the verdict record path, `<run>/verdicts/<lane>/<commit>.json`. So a verdict covers one exact commit.
- **Verdict.** `verdict <lane> --sha S` records the validator's verdict, with the text on stdin. It runs only inside a launched session: it takes the session name and ID that the launcher exports, and the run's session registry must hold that session with the role `validator`. `S` must be the recorded commit. The record keeps the session ID as the verdict's author. A verdict file written any other way has no valid author and never merges.
- **Merge.** `merge <lane>` merges only when all of these hold. The first line of the verdict text is exactly `passed`. "passed with remarks" and "failed" never merge. The author is a session of this run whose only role is `validator` (a worker resumed under a validator record keeps its session ID and is refused), and it is not the lane's worker. The `verdicts` folder, the lane's folder and the record are no links. The lane tip is still the validated commit. Both trees are clean, untracked files included. The integration branch is checked out and is at its last confirmed tip. The run is not stopped, or a `soft:ticket` stop covers the ticket that `ready --ticket` recorded for the lane. Then the engine runs `git merge --no-ff` of that commit and confirms it from the branch ref: the new tip has the old tip and the lane commit as parents, and its tree differs from the old tip. The gate then runs on the merged tree in a throwaway worktree, in its own process group. After the gate, still under the merge lock, the engine reads the verdict again; if it changed, the merge is rolled back. A merge counts only with its `merge-confirmed` ledger line.
- **Author boundary.** The author check stops a worker that uses its own session identity, or a file in the repository, from passing as the validator. It does not stop a process of the same user, a worker included, that sets the two session variables to the validator's values or edits the run folder by hand. D37-FLOW-8a puts that outside the beta's boundary; the owner confirms this reading.
- **Failures.** Exit 65 means the merge was refused and nothing changed (or a changed verdict was rolled back). 69 means the merge would change nothing (a no-op is a failure). 70 means a conflict, a failed git check or a git error, or that the branch is left for a person. 72 means the gate failed on the merged tree. 75 means the run is stopped, the merge was stopped by a signal, or another merge holds the lock. 78 is a config error. On 65 after the gate, 69, 72, 75 and a failed merge or git check (70) the branch is put back to its old tip with `git reset --hard` inside its own worktree, never by moving the ref, and only while the branch is still checked out at its old tip or at this merge's commit, and the worktree is pristine: no uncommitted change, no untracked file and no ignored file (`git status --porcelain --untracked-files=all --ignored` is empty; the engine itself writes no file there). The reset is `git reset --keep`, which also refuses to overwrite a local change. When the branch moved, HEAD is detached or on another branch, or the worktree is not pristine, nothing is reset: it is left for a person (70), the message names the cause and never says "rolled back", and nothing is lost. For the same reason a merge is refused (65) unless the integration worktree is pristine before it starts. After a git confirmation failure only a commit that is provably this merge (parents: the old tip and the lane commit) may be undone. A tip that moved outside the engine, for example after an interrupted merge, refuses every merge until a person puts it back.
- **Signals.** TERM, INT or HUP to the caller is passed to the merge's own subshell. That subshell stops the gate's process group, rolls back as above, releases its lock and exits 75; the caller returns that code. A signal that comes while the gate's worktree is made stops the merge before the gate starts. From the `merge-confirmed` line on, a signal no longer undoes the merge: TERM, INT and HUP are ignored until the tip is written, also when they go to the whole process group (a closed terminal); the ledger line is written by a fresh shell that starts with them ignored. KILL cannot be caught or passed on: after a KILL to the caller the merge subshell runs on and may still confirm the merge.
- **Lock.** One merge at a time per run, under `<run>/merge.lock`. A lock whose holder is dead is taken over in place under `merge.lock/takeover`; a waiter never removes a lock, so it never removes another waiter's new one. A merge removes only its own lock.
- **Gate.** The engine runs the gate command itself, so the command comes only from the user config (D37-FLOW-8): `gate.list.<label>.command`. The project or user config selects the label with `gate.use`. With no gate, the merge is refused. A project config that holds a gate command is refused, and the message says where to move it.
- `status` prints the integration tip and the confirmed merges. Setting the ticket state after a merge, the remote PR merge and the "passed with remarks" flow come later (#59, #60).

## Stops

`bin/harness state <run-dir> stop [--type soft:step|soft:task|soft:ticket] [--ticket ID]... [reason]` records a soft stop (H-086, D25, D25a). The default is `soft:step`.

- **`soft:step`** lets the current step finish. No new step and no new ticket begins, and no merge runs.
- **`soft:task`** works the same in the engine. Its stop text asks the session to stop after its current task inside the step.
- **`soft:ticket`** lets each ticket that began before the stop run to its end: its next steps may begin, their sessions launch, and its lane merges. No new ticket begins. With `--ticket`, only the named tickets go on, and the other tickets get `soft:step`.
- **The newest stop is in force** until `state <run-dir> resume`. While the STOP file exists the run is at least as strict as `soft:step`.
- **Stop text.** The verb prints the stop id and the variant's standard text. It does not deliver it: send it with `session deliver <name> --text "<text>" --id <stop id>`. Hard stops and the own message come later (#67).
- **Step gate.** `state <run-dir> begin --ticket T --step S` asks before a step begins: exit 0 and one `step-begin` ledger line, or 75 when a stop lets nothing new start. An unknown stop state also gives 75. A ticket counts as begun when a `step-begin` line for it, or the launch of a session with `--ticket` for it, comes before the stop.
- `state <run-dir> stop-state` prints the stop in force as one JSON line.

## End of run and standby

`bin/harness lifecycle <run-dir> check` decides what the run does now, acts on it, and prints the decision as the first line (H-079 to H-082, S8-20a, D37-LIFECYCLE-3). The decision is worked out again at every call. Only a run end stays, until a resume.

- **`work`**: a ticket is ready or in progress.
- **`stopping`**: a soft stop is in force, and work it allows still runs. Nothing is closed.
- **`wait-review`**: every remaining ticket waits on review. The worker, validator and question sessions close. The orchestrator and the watcher wait, and nothing is sent to them.
- **`wait-blocked`**: only human-blocked tickets remain. The same as `wait-review`, with no nudges.
- **`standby`**: all tickets are done and standby is on. The finished sessions close. The orchestrator and the watcher keep running, and no other session starts.
- **`end`**: all tickets are done and standby is off, or only human-blocked tickets remain with `on_only_human_blocked` set to `end`, or a soft stop has nothing left to finish. One `run-end` line goes to the ledger, and every session of the run closes. The calling session is never closed by itself; the output names it as `self <name>`.
- **`ended`**: the run ended earlier. A session that could not be closed at the run end (busy, or its terminal could not be reached) is tried again at every later call.
- **`unknown`** (exit 2): the stop state or the ticket queue cannot be read, or the local ticket folder does not exist, and nothing changes.

`lifecycle <run-dir> done <name>` records that a session's task ended and closes it (H-081). It refuses the orchestrator and the watcher, which close only at run end, and a session of another run.

Every close goes through `session close`, by the exact process, over this run's registry only. The run keeps no ticket list of its own: its tickets are those of the queue (`tickets ids <state>`, the folder `<project>/.harness/tickets` unless `HO_TICKETS_DIR` is set).

Settings (OPEN-9): `run.standby` (`true` or `false`, default `false`), overridden for one run by `run new --standby on|off`. `run.on_only_human_blocked` (`wait` or `end`, default `wait`). Both are fixed in `<run>/lifecycle.json` at run start and written once to the ledger as `run-settings`. Any other value is a config error (exit 78).

You do not need to read it before every change.

- session liveness, recovery, closing sessions — section A
- sending instructions to a session — section B
- merge, validation, git operations — section C
- tickets, labels, run state files — section D
- more than one worker, heavy work, Docker — section E
- subscription limits, the limit banner, pause and resume — section F
- worker cap defaults, usage history, timeouts — section G
