This change builds on `harness-stable-beta`: its runtime profiles (D31, D37-RUNTIME-1, D37-RUNTIME-2), the names rule (D37-FLOW-1), the trust boundary (D37-FLOW-8), the model roles (H-150, D48), the check after each action (H-148, D46), the confidence log (H-149, D47) and the readiness check (H-154, D52).

## Goals / Non-Goals

**Goals:**
- Codex works at the same level as Claude Code in a flow with interactive terminals, as orchestrator and as worker.
- Terminal control keeps working after runtime updates, by finding and recording corrections.
- Work goes to the runtime and model that fit it, inside limits the person set, and within each provider's rules.
- The plugins install in Codex too.

**Non-Goals:** see proposal.md, Non-goals.

## Decisions

- D53 — Codex at the same level (H-155, H-156, H-157, H-075): the beta Non-goal "Interactive Codex sessions" and the "experimental" wording of D30 and D37-RUNTIME-2 end with this change. The orchestrator is one procedure for both runtimes. Each runtime differs only in its runtime profile: launch and resume lines, transcript location, the liveness source (Claude Code hooks; for Codex, the transcript's turn-complete event and its Stop hook), the limit source (for Codex, the rate-limit data in the transcript, read by window length, because the installed Codex reports its weekly window as the primary one), and the screen data. A Codex orchestrator needs shell access to tmux and iTerm2, so the Codex runtime profile names the sandbox and approval settings that allow it. They are never taken from Codex defaults, and a profile from a project config is never used (D37-FLOW-8). Codex hooks load only after the person trusts them, so the setup asks for that trust once, as a choice inside its runtimes question (Q1 of D51), not as an extra prompt, and the transcript event stays the liveness source when hooks are not trusted. The first task is a spike that captures Codex screen fixtures, because the research could not start Codex to see its idle screen. The spike also tests the runtime's own queue command for an existing session; if it works, delivery prefers it over typing, in line with H-101. Under a Codex orchestrator, the context watcher of D32 is a Codex session too, so the pair restarts each other without the opt-in of H-162. The comparison run of D37-RUNTIME-2 stays, as the check that both runtimes give the same result (RP3.22). Codex execution stays marked experimental until both the Codex success path and the comparison run pass in a release. Test depth follows the owner's words: Claude Code as orchestrator is tested in full; Codex is tested on its main success path, as orchestrator and as worker, on tmux and iTerm2; a Codex orchestrator launching Claude Code is built behind the opt-in of H-162 and not tested (owner decision 2026-11-26 for the parity and the test depth; the profile split and the spike: agent decision; research 2026-11-27, R2 part 2).
- D54 — Self-correcting terminal control (H-158): a correction is one record in a `corrections.jsonl` file in the user state folder, keyed like the confidence log of D47: terminal app and version, runtime and version, operating system, action kind. It holds what failed, what worked instead, the evidence (the saved screen file) and who approved it. Learning runs only in flows with interactive terminal sessions (RP3.6). When an action fails on a key, the orchestrator first tries the corrections recorded for that key, then the default way, then a search: it reads the screen with the cheap checker, tries the ways listed in the runtime profile, and, if those fail, asks a strong-role model for one more way. Screen text reaches any model only inside the untrusted fence (D37-INTAKE-1). A correction is built only from a fixed list of action kinds: wait, read again, use another delivery route the profile lists, resume by ID, or send a named key from the runtime profile. A key is sent only when every check that H-099 requires before typing passes: the session is idle, the input line holds no draft, and no dialog is open. An interrupting key (one that stops a turn or clears the input line, such as Escape or Ctrl-C) is never part of a correction. A key is never sent on a model's answer alone (D46). It never holds free text to type and never a shell command. A correction must pass an exact check (D46 level 1) before it is kept. A way that works is recorded. With the setting `ask`, it is used for this run and kept only after the person's yes. With `automatic`, it is kept at once and listed in the run summary. With `off`, nothing is kept. A correction can never type into a busy session or a draft, close a busy session, or skip a check; such a correction is refused and the refusal is logged. The learning command reviews the failures of recent runs and proposes corrections in one list. This follows the reflection and skill-library pattern from the research (Reflexion, Voyager): store what worked and reuse it, keyed so that a version change does not reuse a stale fix blindly (owner decision 2026-11-26 for learning and its settings; the structure: agent decision, "сам придумай структуру"; research 2026-11-27, R2 part 5).
- D55 — Missing skill on one runtime (H-159, H-078): the readiness check (D52) lists each step, its runtime and what is missing. The readiness check only reports. The start check and the setup then offer both choices when they exist, inside the final save question of D51, not as extra prompts: set up (after a yes, D49) or move the step to the runtime that has the item. A step fixed to a runtime (D56) gets only the setup choice. A move made here is recorded in the run ledger and lasts for the run; to keep it, the person saves it in the flow config through `/harness:config` (agent decision on the owner's answer).
- D56 — Load routing (H-160): the flow config gets a `routing` block: `split` (the preferred runtime for each step, defaulting to the step's `runtime` field), `fixed` (steps that never move) and `may_change` (false by default). The setup asks about it only when two runtimes are ready (Q1 of D51). `may_change` and `fixed` are recorded fields of the approval record of D37-FLOW-8, so a committed config cannot raise them without the person's yes on this machine. With `may_change` true, the orchestrator may move a movable step for three reasons: the step's skill is missing on its runtime (D55), the runtime's account is past its threshold (H-110) while another runtime has room, or the runtime is out of service. It writes a ledger line with the reason and sends one notice for each change. Without the permission, an attended run asks, and an unattended run keeps the split and logs the reason. The permission is given once, at setup, with its limits: the owner's words read as a permission given at setup, and asking at each change would stall an unattended run (agent decision on the owner's answer; the reading is stored as a question for the owner).
- D57 — Current model list (H-161): no public source holds roles or tiers; they give what exists, its price, its features and its deprecation. The tools the research could check keep roles in their own config, made by hand; one tool picks models itself, and several were not checked. So the roles stay in the harness's own `models.json` (D48), and public sources only check it. Primary source: models.dev (MIT licence, with recent commits; has family, release date, status and cost). Second opinion: the LiteLLM model price file (MIT licence outside its enterprise folder, has deprecation date and successor). The runtimes' own lists come first for what this installation can run (for Codex, its local model cache). The check runs at setup and at most once a day at run start, downloads whole files with a cache, and writes a proposed change: a gone or deprecated model, a newer model of the same family, or a price outside the role's price band. The mapping changes only after the person's yes. An unreadable source never stops a run. Leaderboards are not used to assign roles (agent decision on the owner's answer; research 2026-11-27, R2 part 1).
- D58 — Other models inside a runtime (H-163): a runtime profile may have variants. A variant names the provider, the endpoint kind and the environment it needs, by label only; the values live in the user config (D37-FLOW-8, D37-SESSIONS-5). Examples: Claude Code with an Anthropic-compatible endpoint from another vendor; Codex with another model provider or a local model. A variant can be the target of a role in `models.json` and of routing. The session record names the runtime and version, the variant, the provider, the model requested, the model that ran, the effort and the billing path. At setup the harness shows that the runtime's vendor does not support such a setup, where that is so (Anthropic states it does not support routing Claude Code to non-Claude models through a gateway), and the variant's known gaps. It also shows that the screen text read by a checker on that variant goes to that vendor (agent decision on the owner's answer; research 2026-11-27, R2 part 3).
- D59 — Subscription routing (H-162): the research read both providers' terms on 2026-11-27. OpenAI's terms forbid circumventing rate limits; Anthropic's terms and usage policy forbid bypassing protective measures and creating several accounts to circumvent guardrails, and its Claude Code page says plan limits assume ordinary, individual use. Moving work between two subscriptions of one provider to get around a limit is therefore not offered. Routing across providers is offered. API billing has no subscription window to get around, so the person may turn on routing within one provider with `routing.same_provider: api_billing`. This setting is read only from the user config, never from a project config, because it changes the person's billing (D37-FLOW-8); the setup shows that this needs API credits, and each session record names its billing path. The same setting allows a Codex orchestrator to launch Claude Code sessions. A fixed account per role (D37-SESSIONS-5) is the person's own setup, not load routing, and stays as it is. The harness never reads or passes on another tool's login token. This is not legal advice; the setup text says the person is responsible for their own plans (owner decision 2026-11-26 for the rule and the opt-in; the terms reading: research 2026-11-27, R2 part 4).
- D60 — Codex install (H-164): the installed Codex has a plugin command and a marketplace, and its documentation calls the Claude marketplace file format compatible. So the first step is not npm. Phase 0: install the current marketplace into a throwaway Codex home and record what works. Phase 1: make each skill self-contained: its scripts inside the skill folder, no Claude-only variables in skill text (the plugin root variable, `$ARGUMENTS`), and a tool map per runtime where a skill uses a tool that only one runtime has. Phase 2: add the Codex marketplace file next to the Claude one, with the same plugin names, sources and versions, and a test that keeps them in sync. Claude Code users keep `/plugin update`: the marketplace name, plugin names and sources do not change, and each changed plugin gets a version bump. Slash commands, agents and hooks stay Claude-only where Codex has no equal, and each README says so. Phase 3: an opt-in cross-tool probe test, proven by a mutant. An npm package is a later option, as a transport the marketplaces accept, only if a plugin needs file conversion. The harness engine still launches Claude Code and reads Claude limits, so a harness installed in Codex runs Codex-only flows only after D53 (agent decision on the owner's answer; research 2026-11-27, R3).

## Risks / Trade-offs

- Codex screen and sandbox behaviour are not verified yet; the spike (tasks 1.1, 1.2) comes before any build work.
- Learning that is automatic can keep a wrong correction; corrections are keyed by version and can never weaken a safety rule.
- The model list check depends on outside data; a failed read changes nothing.
- The Codex marketplace compatibility is read from documentation and the binary, not from a real install; phase 0 checks it.
